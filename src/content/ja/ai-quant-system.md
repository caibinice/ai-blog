AIクオンツに触れ始めた頃、私が最も惹かれたのは結果だった。上向きの資産曲線、見た目の美しいリターン指標、あるいは「モデルが市場の法則を発見した」といった言葉。しかし実際に手を動かしてみると、クオンツプロジェクトで最も難しいのは、何かの数式を書き下すことではなく、もっと素朴な問いに答え続けることだと気づいた。データはいつ取得したのか？タスクが失敗しても再実行できるのか？モデルの判断は遡って検証できるのか？バックテストは未来を見てしまっていないか？

これらの問いはどれも華やかではないが、システムが信頼に足るかどうかを決めてしまう。そこで私は、このプロジェクトを単独の銘柄選択ページとしてではなく、一つの研究システムとして構築することにした。復査でき、再現でき、問題を見つけたときには証拠を差し出せるシステムだ。

## ひとつながりの研究ループ

フロントエンドにはReactとViteを使い、相場、銘柄プール、ファクターランキング、センチメント、バックテスト、Walk-forward、タスク状態、学習コースを表示する。FastAPIバックエンドは明確なインターフェースの役割に徹し、実際に時間のかかるデータ同期やモデル分析、バックテストは独立したワーカーが実行する。MySQLは結果の保存場所であると同時に、タスク状態、データバージョン、学習の進捗も保持する。

ある研究タスクのライフサイクルは次のようになる。

1. 画面から研究パラメータを送信し、APIがタスクを `queued` として書き込む。
2. ワーカーがタスクを引き受け、状態を `running` に更新する。
3. データ取得、センチメント分析、バックテストの進捗が段階的に書き戻される。
4. 成功すれば構造化された結果を保存し、失敗した場合は読み取り可能なエラーを記録して再試行できるようにする。
5. ページを更新しても、サーバーを再起動しても、タスクの状態はそのまま残る。

![研究タスクのデータフローとライフサイクル：Frontend → FastAPI → シングルワーカー → MySQL、状態は永続化され、失敗は再試行できる](/images/ai-quant-system-flow.svg)

この設計は極端なスループットを狙ったものではない。サーバーは2コア2GBで、シングルワーカーで逐次実行するほうがむしろ制御しやすい。相場データの取得、大規模モデルへのリクエスト、pandasによるバックテストが同時にメモリのピークを作ることもなく、失敗がどのレイヤで起きたかも特定しやすい。

## 状態機械こそがこのシステムの土台だ

タスクを一回きりの関数呼び出しではなく、状態を持つオブジェクトとして扱うこと。これが設計全体で最も重要な一手だ。それぞれの状態は明確なDB書き込みに対応する。送信時に `queued`、引き受け時に `running`、終了時に `success` か `failed`。状態はどこかのプロセスのメモリではなく、データベースの一行として存在する。

ここには見落とされがちな利点がある。プロセスはいつ死んでもよい、ということだ。ワーカーのクラッシュ、マシンの再起動、私が誤ってサービスをkillしてしまっても、タスクの状態がそれに巻き込まれて消えることはない。再起動後、生きたプロセスを伴わずに `running` のままのタスクは中断とみなして再キューできるし、`success` と `failed` はそのまま残る。つまり「状態は再起動後も残る」は宣伝文句ではなく、状態をデータベースに置くという決定の自然な帰結にすぎない。

![研究タスクの状態機械：queued → running →（success または failed）、失敗は queued へ再試行でき、成功はDBに永続化される](/images/ai-quant-system-state.svg)

失敗のステップは、あえて饒舌にした。タスクが失敗したとき、私は状態を `failed` に変えるだけでなく、人が読めるエラーメッセージを同じ行に書き込む。データソースのタイムアウトなのか、ある銘柄の売買停止でデータが欠けたのか、バックテスト区間に異常値が現れたのか。翌日戻ってきたとき私が読むのは「なぜ失敗したか」であって、空っぽの赤い点ではない。

再試行には冪等性が要る。タスクを再実行して、DBに中途半端な結果が二つ残ってはならない。私のやり方は、各実行がまずこのタスクが以前書き込んだ派生データを片付けてから再計算するというものだ。生データは補うだけで、上書きはしない。この遷移を疑似コードで示すとこうなる（あくまで例示）。

```python
# 例示：タスクの状態遷移。実プロジェクトのコードではない
def run_task(task):
    task.mark("running")              # 引き受け、DBに書き込む
    try:
        clean_previous_outputs(task)  # 再試行の冪等性を保つ
        result = execute(task)        # 取得 / センチメント / バックテスト
        task.save(result)
        task.mark("success")          # 構造化結果を永続化
    except Exception as e:
        task.mark("failed", error=readable(e))  # 読めるエラー
        # ここで黙って握りつぶさず、人か再試行方針に委ねる
```

## データにもバージョンを持たせる

「最新のデータ」だけを保存していると、昨日のバックテストは二度と誠実には再現できない。足元のデータが変わってしまっているからだ。だから私はデータにも取得時刻とバージョンを刻む。一度の取得は識別可能なバッチであり、バックテストが参照するのは「そのとき偶然そこにあったもの」ではなく特定のバージョンだ。

この価値はデータを差し替えるときに初めて現れる。「別のバッチのデータでも実験は再現する」と言えるのは、古いバッチがまだ存在し、名指しで参照できることが前提だからだ。データのバージョン管理は派手なものではない。「再現可能」を願望から、実際に確認できる性質へと変えるだけのものだ。

## AIには「監査可能な判断」を任せる

私は大規模モデルを主にニュースや公告の構造化抽出の層で使っている。モデルはポジティブ、中立、ネガティブのラベルを出力し、スコアや確信度、要約、理由もあわせて返す。モデル結果はモデル名と分析時刻付きで保存され、原文もそのまま保持される。

フィールドは意図して設計している。ラベルのほかに、スコア、確信度、要約、理由、モデル名、分析時刻を残す。こうすれば一つ一つの判断が自らの文脈を携える。誰が、いつ、どれほどの確信で、どの一文に基づいて出したのか。例示的な抽出結果はおおむね次のようになる（フィールドは例）。

```json
{
  "label": "bullish",
  "score": 0.62,
  "confidence": 0.71,
  "summary": "四半期の売上ガイダンスを上方修正",
  "reason": "公告は来四半期の出荷がコンセンサスを上回ると見込む",
  "model": "llm-extractor",
  "analyzed_at": "2026-05-11T09:20:00Z"
}
```

ここで守り続けている原則がある。原文は不変、派生は再計算可能、というものだ。原文は事実であり、保存したら二度と変えない。ラベルやスコアはすべて原文から導かれるものだから、モデルを替えたりプロンプトを変えたりしても、同じ原文の集合に対して改めて走らせ、新しい派生結果を得られる。源を汚す心配はない。

これにより、私は次の二つを切り分けて検証できる。

- モデルがテキストから実際に何を読み取ったのか
- ストラテジーがその構造化情報をどう使っているのか

ポジション管理や売買ルールは、依然として確定的なファクターの組み合わせとバックテストコードが担っている。この責務の境界は意図して引いたものだ。AIは非構造化テキストから傾きを読み取るのが得意だが、その出力には不確実性が伴う。一方でファクター計算とバックテストは確定的でなければならない。同じ入力からは常に同じ出力が得られること。さもなければバックテストは意味を失う。AIには抽出を、確定的なコードには意思決定を任せれば、両者の誤りが互いを覆い隠すことはない。このやり方は“完全自動”とは言えないかもしれないが、結果に異常があったときに証拠をたどることができ、結論だけを返すブラックボックスに直面せずに済む。

## 研究システムは学習システムでもあるべき

このプロジェクトには、全11章のゼロベース向けコースと実行可能な実験も組み込まれている。ローソク足やPythonとpandasの基本から始まり、信頼できるバックテスト、センチメントファクター、Walk-forward、研究のエンジニアリングへと進む。学習の進捗はまずブラウザに保存され、APIが利用可能になった時点でMySQLに同期される。

このコースは実のところ能力の階段だ。まずローソク足を読め、pandasで時系列を扱えるようになる。次に一度のバックテストが何をもって「信頼できる」のか（未来を覗かない、生存バイアスがない）を理解する。そこで初めてセンチメントをファクターにし、Walk-forwardでそれが単なる過学習でないかを検証できる。最後に研究のエンジニアリング——本稿がずっと語ってきた、タスク・状態・バージョンという地味な土台——にたどり着く。順序は逆にできない。信頼できるバックテストを飛ばしてファクターを追えば、捕まえるのはたいてい自己欺瞞だ。

私は次第に一つの考え方を強く持つようになった。真の成果は、あるバックテストで高いリターンが出たことではなく、明日、別のデータ、別の時間窓、さらには別のマシンに切り替えたとしても、実験を説明し、再現し、その限界を認められることだと。

## 現在の境界

このシステムは研究と教育のみを目的としており、証券会社との接続はなく、実際の取引を実行することもない。これは怠慢ではない。実際の発注が直面する問題を、教育用システムは真剣に扱っていないからだ。売買停止中の注文はどうなるか、ストップ高・ストップ安で約定するか、大口注文のインパクトコストはどれほどか、戦略のキャパシティはどこで尽きるか、データライセンスは実運用まで覆っているか、相場フィードが切れたときどう安全に復旧するか。そのどれか一つでも、紙の上では美しい戦略を現実の市場で損させうる。

それらが整わないうちに「自動発注」を行うのは進捗ではなく、証拠を飛び越えることだ。私はこのシステムを、本物の資金につなぐことを急ぐより、「説明でき、再現でき、追跡できる」場所に留めておくほうを選ぶ。

現在稼働中のバージョンは [/quant/](/quant/) で見ることができる。これは答えを約束する機械というより、改装を続ける実験室に近い。
