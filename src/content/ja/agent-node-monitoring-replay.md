ワークフローが正しい答えを返せるようになったあと、とても現実的な問題に直面した。技術共有の場で、聴衆は「599 元は返金可能」という結果を見ても、それがどう導かれたのか分からない。そもそも注文を照会したのか？ 二回目でなぜツールが変わったのか？ 三人の専門家はそれぞれ何の情報を受け取ったのか？

バックエンドのログを見れば確認できるが、説明の最中にターミナルと Web ページを行き来していると、すぐに注意がそがれてしまう。そこで私はスマートコックピットの Graph ワークベンチに、構造化された実行記録を加えた。リアルタイムでノードの流れが見え、終了後は任意のステップで止めて入力と出力を確認できる。この記事では主に、実装中に紛らわしかった境界をいくつか記録する。

記録の対象はカスタマーサービスの完全なメイングラフであり、共有時に重点的にデモするツールループとマルチ Agent だけではない。RAG、画像、レポート、人的引き継ぎ、そして二種類のフィードバックループも、すべて同じノードラッパーを通り、同じイベント列に入る。そうして初めて、同じ UI の上で「直接証拠を取れた場合」と「失敗してもう一周した場合」の違いを比較できる。

## まず監視・リプレイ・復帰を区別する

![スマートコックピットのノードグラフと詳細パネル：ハイライトは実際の実行イベントに由来する](/images/cockpit-agent-monitor.png)

**監視**は、バックエンドが現在実行しているタスクを観察することだ。**リプレイ**は、既存の記録を閲覧することで、バックエンドが再度注文を照会したりモデルを呼び出したりはしない。**人手による復帰**は、新しい情報を送信してバックエンドに復帰グラフの実行を継続させることで、新しいイベントが発生する。

画面上の「リプレイ一時停止」はフロントエンドのカーソルを止めるだけで、「現在のワークフローを停止」して初めてバックエンドにタスクのキャンセルを要求する。誤解を避けるため、詳細の「現在の状態」も最新状態であると明示している。リプレイに合わせて巻き戻ることはない。履歴ノードの入力と出力は確認できるが、この版は完全な状態の time-travel ではなく、任意のノードから業務を再実行できるものでもない。

## まず八つの入口で記録が十分か確認する

受け入れ時には、ノードが緑になったかを見るだけでなく、シナリオごとに実際に起きたことを探した：

| シナリオ | 同じ記録の中で確認すること |
|---|---|
| 製品知識 RAG | `retrieve` が返した知識の出所、スコア、クエリ；回答がどの証拠を使ったか |
| 画像とテキスト | `vision` の画像観察が次の分類と検索コンテキストに入ったか |
| 企業レポート MCP | `report_mcp` の実際のレポート結果であり、モデルが「調べた」と主張したことではない |
| ツール呼び出しループ | 各ラウンドの `tool_execute` のツール名、引数、観察結果、異なる Span |
| マルチ Agent 協調 | 三人の専門家パス、外側の親 Span、サブグラフノード、最終集約 |
| 人的引き継ぎ | `run.waiting`、引き継ぎ資料、`run.resumed`、`human_reply`；前段の動作が重複しないこと |
| フィードバック駆動の再検索 | 二回の `retrieve` の間に確かに `requery` があり、クエリテキストが実際に変わっていること |
| ツール異常と予算 | 失敗した観察が保持されているか；三ラウンドの復帰と二ラウンドの人的引き継ぎが異なる出口を通ったか |

各シナリオが終わったあと、私は毎回履歴を開き直し、JSON をエクスポートし、同じリプレイバーでゼロまで戻してから完了ノードまで進めた。リプレイ中に新しいモデル呼び出しや注文リクエストは発生しない。人手待ちのタスクも停止でき、すでに放棄すると決めたのに待機状態のまま残るデモ記録を避けられる。

知識の保守と共有ガイドはワークベンチの入口であり、メイングラフに詰め込む二つの Agent ノードではない。前者は検索可能な資料を準備し、後者は入力を読み込む。監視が必要なのは、これらの入力が Graph に入った後の実行事実だ。この境界をはっきりさせれば、ページナビゲーション、業務実行、呼び出し追跡が混ざりにくくなる。

## 最終的にノードの色を遠隔操作するのではなく、イベントを記録することを選んだ

ノードは一律にラッパーを通る。ノードに入るときに入力を記録し、終わるときに戻り値の差分と所要時間を記録し、例外を投げたときに失敗を記録する。同じロジックがメイングラフと専門家グラフを包み、各業務関数に監視コードを重複して書かなくて済む。

以下は切り詰めたロジックであり、そのままコピーできる完全なクラスではない：

```java
String span = newSpanId();
emit("node.started", nodeId, path, span, input);
long started = System.nanoTime();
try {
    Map<String, Object> delta = businessStep(input);
    emit("node.completed", nodeId, path, span,
         Map.of("output", delta, "durationMs", elapsed(started)));
    return delta;
} catch (Exception e) {
    emit("node.failed", nodeId, path, span, publicError(e));
    throw e;
}
```

モデルリクエストは別途 started/completed/failed、およびモデル名、用途、Token 使用量を記録し、親 Span は所属ノードを指す。ここに示すのはリクエスト、公開結果、構造化された意思決定であり、モデル内部の思考ではない。グラフの静的定義は `/api/workflow/graph` が提供し、ノード位置は事前設定され、実行イベントがどの辺を通り、どのノードが完了したかを決める。

私はあえて「状態差分」という言い方を残した。`node.completed.output` はこのノードがどのフィールドを変えたかを示すだけで、完全な State とみなすと、見直しのときに他のフィールドが失われたと誤解してしまう。

## ループの中では、ノード名だけでは足りない

ツール分岐は `tool_execute` を二度通り、注文専門家の内部でも同じ名前を使う。nodeId で入力と出力を対応付けると、遅かれ早かれ第一ラウンドの入力を第二ラウンドの結果に紐づけてしまう。

現在の記録には、いくつかの異なる階層の識別子がある：

| フィールド | コックピットで何を区別するか |
|---|---|
| traceId | 実行全体；本プロジェクトでは Run ID と同じ |
| nodeId | 業務ノード、例えば tool_execute |
| spanId | この具体的な実行であり、このノードの永久 ID ではない |
| parentSpanId | モデルリクエストや子ノードがどの外側呼び出しに属するか |
| path | メイングラフの root、または root/toolAgent[3] のような専門家パス |
| seq | 同一 Run 内で増加するイベント番号。再送と重複排除に使う |

入力と出力は **spanId + path** で対応付ける。専門家のライフサイクルマーカーは外側 specialist の Span を再利用するが、パスが異なるので、対応付けのときに path を加えれば外側の状態全体を取ってしまうことはない。パス内の `[3]` は今回のタスク番号であり、注文専門家が固定で三番目というわけではない。

これで別の習慣も改めた。すべての duration をそのまま合計することだ。外側 specialist の所要時間にはすでにサブグラフが含まれており、親子を一緒に足すと二重計算になる。ページのエンドツーエンド所要時間はイベント区間を取り、ノード所要時間は一回の呼び出しか同名ノードの累計を説明する。両者は基準が異なる。

## ログから SSE へ、最も気にするのは一部を欠落させないこと

各 Run は `RunStore` に順序付きで追記されるイベントを保存する。`emit` は Run ロック内で seq を割り当て、記録を追記し、購読者に通知する。新規購読も同じロック内で、まずカーソル以降の履歴を再送し、それからリアルタイム購読に加わる。

これで対処しているのは小さくても現実の競合状態だ。履歴の再送が終わって先にロックを解放し、しばらくしてから購読者を登録すると、その間に到着したイベントはどちらにも受信されない可能性がある。

コックピットの元バックエンドは WebFlux なので、統合時にデモプロジェクトの MVC `SseEmitter` は使わず、`Flux<ServerSentEvent<...>>` を返す。プロトコルは依然として単純だ：

```text
id: 19
event: trace
data: {"seq":19,"type":"node.completed","nodeId":"tool_execute",...}
```

ブラウザは `EventSource` で `trace` を受信し、seq で重複排除する。再接続時、サーバーは `after` と `Last-Event-ID` の大きい方を取り、それ以降のイベントだけを再送する。人手待ちの間は業務イベントがないため、15 秒の ID なしハートビートがプロキシ接続を保つ。五分のストリームが終わるとブラウザは再接続できる。ハートビートは実行カーソルを進めない。

レスポンスには `X-Accel-Buffering: no` と no-cache も設定し、汎用 Nginx プロキシがイベントを溜め込んで送信しないのを避ける。ここを検証しないと、ページは最終完了時に突然「チェーン全体が一斉に点灯する」ことがあり、リアルタイムに見えても実際には過程を取り逃している。

## リプレイは最初に思ったより単純で、境界もより明確だった

![スマートコックピットが注文専門家のあるツール結果で停止：イベントカーソル、入力と出力、呼び出しパス](/images/cockpit-agent-replay.png)

フロントエンドは常に受信した完全な events を保持する。リアルタイムビューは全イベントを使い、リプレイビューは配列のプレフィックスを使う：

```ts
const visibleEvents = computed(() =>
  trackLive.value ? events.value : events.value.slice(0, cursor.value)
)
```

ノードの色、実行回数、通った辺、ツールのラウンド、専門家カードはすべて `visibleEvents` から計算する。同じカーソルの下では、どこも同じ記録の一部を見ているのであり、それぞれにアニメーションタイマーを用意する必要はない。

カーソルは**配列の位置**であり、seq ではない。一つのノードは辺の通過、started、completed など複数のイベントを残す。一歩進むときは次の `node.completed` がある位置を探すのであり、単純に番号を一つ増やすのではない。連続再生は現在 600ms ごとに一イベント進む。説明しやすい速度であり、元の実行時間の再現ではない。

リプレイ中も SSE で新イベントを受信できるが、カーソルは自動で動かない。Live を押して初めて最新記録に戻る。したがって再生の一時停止は Graph を止めず、後続イベントの欠落も引き起こさない。専門家パスの絞り込みは現在タイムラインと詳細に作用し、メイングラフは依然として nodeId で集約する。デモのときはこの違いをはっきり説明する。

ツールのタイムアウトにはもう一つ細かい点がある。業務コードに捕捉されると `toolOutcome.ok=false` を返す。このときノード自体は「失敗した観察を一つ生成する」責務を完了しているので、イベントは `node.completed` だが、ツールカードは失敗を表示する。ノードが緑かどうかだけでは、業務動作の成功を判断するには足りない。

全シナリオのオンライン回帰では、誤解しやすい失敗も見つかった。最初の三ラウンドですでにタイムアウトの再試行、注文照会、599 元の試算まで終わっていたのに、最後の `review` ノードで終了した。記録を先へ追うと、原因は native thread の生成失敗であり、返金ツールの再タイムアウトではなかった。Graph、HTTP、SSE、MCP が使うスレッドの合計がプロセスの上限に達していた。コックピットの上限だけを 90 から 128 に増やし、CPU とメモリの上限は保ったまま、八つのオンラインシナリオを再実行した。業務ループの予算と実行環境のリソース予算は別物だ。ノード記録があれば、あらゆる失敗をモデルのせいにせずに済む。

## 永続化がどこまでできているか、その分だけ約束する

ルートノードの境界、実行終了、人的復帰、キャンセルは JSON を保存し、まず一時ファイルに書き、それからアトミックに置き換える。本番ファイルは `shared/workflow/runs` に置かれ、release のクリーンアップに従わないので、フロントエンドや JAR を更新しても履歴を読める。

これは完全なイベントデータベースではない。emit のたびにすぐディスクに書くわけではないので、突然終了すると最後のチェックポイント以降のイベントが欠落する可能性がある。起動時に残った RUNNING を INTERRUPTED とし、人手待ちの状態は保持する。復帰は保存されたアプリケーション状態を使って `HumanResumeGraph` に入るのであり、フレームワーク原生のチェックポイントが任意の位置からの続行をサポートしているわけではない。

現在は最大 100 件の実行を保持し、API は直近 40 件を表示する。記録から内部制御フィールド、元画像、api-key を除去するが、汎用の機密情報スキャナではない。スクリーンショットの顧客、注文、レポートはすべてサンプルだ。今後実際の業務資料を扱うなら、フィールド単位のマスキング、アクセス権限、保持期間を別途設計する必要がある。

最初は共有を分かりやすくしたいだけだったが、最後にはこの記録がデバッグにも同じくらい役立つと分かった。モデルの提案と実際の実行が一致しているか、検索リトライでクエリが変わったか、失敗後に期待した出口へ進んだかを確認できる。きれいなノードグラフは後回しでよく、まず実行事実といくつかの ID を正しく記録してこそ、リプレイに信頼できる基礎ができる。
