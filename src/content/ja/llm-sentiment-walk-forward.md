大規模モデルをクオンツプロジェクトにつなぐとき、一番わかりやすい問いかけは「この株は上がる？ 下がる？」というものです。この問いはとても魅力的に見えます。なぜなら、答えがそのまま最終決定に見えるからです。しかし初心者にとっては、それがいちばん検証しにくい問いでもあります。モデルが間違った事実を参照しているかもしれず、時間の境界があいまいになりがちで、同じプロンプトでもバージョンが変われば異なる結論を出す可能性があります。

やっかいなのは、この問い方が二つの別々の仕事を一つに混ぜてしまう点です。ひとつはテキストから「何が起きたか」を読み取ること、もうひとつはその出来事が価格にとって何を意味するかを判断することです。前者は言語理解であり、モデルが本当に得意とするところです。後者はコスト・遅延・リスクを伴う意思決定であり、バックテストで検証できるルールが担うべきものです。両者を一つの質問に束ねてしまうと、各ステップを個別に検証する機会を捨てることになります。

私はその後、より抑制のきいた道を選びました。大規模モデルには情報抽出を任せ、直接ポジションをコントロールさせないことにしたのです。

## テキストを監査可能なイベントに変える

ニュースやリリースがシステムに入ると、まず原文、ソースのリンク、配信日時、コンテンツのハッシュをそのまま保存します。モデルはテキストを読み取り、次の項目を出力します。

- ポジティブ・中立・ネガティブのラベル
- 正規化スコア
- 信頼度
- 要約と判断理由
- モデル名と分析時刻

これらのフィールドは元のニュースを上書きせず、独立した派生データとして残ります。将来モデルやプロンプトを変更するときには、同じテキストに対して再分析し、異なるバージョンの解釈を比較できます。

「原文」と「派生データ」を分けることは、私が何度も立ち返る規律です。原文は書き換えられない証拠であり、自身の配信時刻を持ちます。派生データは再計算できる解釈であり、モデル名と分析時刻を持ちます。モデルの判断を原文フィールドに書き戻した瞬間、あるスコアがどのバージョンのモデルによって、いつ出されたものかが二度と言えなくなります。それこそバックテストで最も問いただしたい点なのです。理由（reason）フィールドも飾りではありません。あるアウトオブサンプルの取引が意外な結果になったとき、この理由をたどって原文に戻り、モデルが事実を読み違えたのか、事実そのものに価値がなかったのかを見分けられます。

出力の契約は、たとえば次のように素朴に書けます。フィールドを固定しておけば、あとで構造チェックがしやすくなります。

```json
{
  "event_id": "sha1(raw_text)",
  "published_at": "2026-03-11T09:20:00Z",
  "source_url": "https://…",
  "label": "bullish",          // bullish | neutral | bearish
  "score": 0.62,               // [-1, 1] に正規化
  "confidence": 0.71,          // [0, 1]、例示値
  "summary": "…",
  "reason": "…",              // 検証可能な根拠
  "model": "llm-vX",
  "analyzed_at": "2026-03-11T09:24:10Z"
}
```

このステップの最大の価値は「AIが賢い」ことではなく、自然言語による判断をスクリーニング・集計・テスト・批判ができるデータに変換することにあります。「ポジティブ」としか言わないブラックボックスはバックテストできませんが、タイムスタンプ・ソース・信頼度を備えたイベント表ならできます。

## 時間こそが最初の規律

ニュースの配信時刻は、戦略が判断を下す時刻より必ず前でなければなりません。当たり前に聞こえますが、実装は落とし穴だらけです。クロール時刻は配信時刻ではありませんし、同じリリースがプラットフォームによって数時間ずれて届くこともあります。バックテストが「公開された時刻」ではなく「私が取得した時刻」を使ってしまえば、そこに未来情報がひそかに紛れ込みます。

重複して転載された記事は除外し、同じ出来事に関する複数の報道を独立した複数回のシグナルと数えてはいけません。ここでコンテンツハッシュが働きます。ほぼ同一の本文は一つのイベントにまとめられ、各社の転載は同じイベントの複製にすぎず、三つの独立したシグナルではありません。重複を除かなければ、大量に転載された一件のニュースがセンチメントスコアで何度も数えられ、偽の「コンセンサスの強さ」を作り出してしまいます。

センチメントも永続的ではありません。7日前のニュースと、たった今出たリリースを同じ重みで扱うべきではないのです。そこでシステムは、イベント時刻をもとに減衰ウィンドウを構築し、ニュースが古くなるにつれて重みを下げ、銘柄ごとにセンチメントスコアを集約します。ひとつの例示的なやり方は、各イベントに指数減衰の重みを与えることです（下の式はあくまで例であり、半減期は訓練期間で選ぶべきで、テスト期間に合わせて調整してはいけません）。

```text
w(t) = exp(-λ · Δt)          # Δt = 判断時刻 − イベント時刻（日）
score_stock = Σ_i  w(t_i) · confidence_i · score_i   （その銘柄の全イベントを合計）
```

![センチメントの時間減衰ウィンドウ：イベントが古くなるにつれて重みが下がり、同一イベントの複数報道は重複除去される](/images/llm-sentiment-decay.svg)

どのバックテストでも、三つの時刻を明確にしなければなりません。ニュースがいつ利用可能になり、いつファクターに組み込まれ、いつ次のサイクルのポジションに影響するか、です。私は「このニュースを使った」と大まかに言うのではなく、これらを分けて記録するようにしています。時間の順序がひとつでも間違っていれば、どんなに正確なテキスト分類も未来情報を作り出しているに過ぎません。

## 「AIあり」と「AIなし」を比較する

ラベルの正確さは、そのまま取引上の価値になるとは限りません。モデルがあるリリースのセンチメントを完璧に読み取れても、その情報がすでに価格に織り込まれていたり、もたらす超過リターンが回転コストを賄えなかったりすれば、戦略にとっては増分ゼロです。「役に立つのか」に答えるには、対照実験しかありません。

私の実験では、まず価格と財務データだけを使ったベースラインを構築し、その上でセンチメント因子を追加し、**同じ銘柄プール・同じコスト・同じウィンドウ**の条件で比較します。変数を制御することが肝心です。二つの群の唯一の違いはセンチメント因子そのものだけであるべきで、そうでなければ勝ったとしても、どこで勝ったのか分かりません。比較する項目は次のとおりです。

| 観点 | ベースライン（AIなし） | センチメント追加 | 私が問いたいこと |
| --- | --- | --- | --- |
| OOS 累積 / 年率リターン | 基準 | 対照 | 増分はプラスか |
| 最大ドローダウン / ボラティリティ | 基準 | 対照 | 変動の拡大とリターンを交換したか |
| 回転率 / 追加コスト | 基準 | 対照 | 増分はコストを賄えるか |
| 異なる相場局面 | 基準 | 対照 | 全期間で有効か、一局面だけか |
| 呼び出しコスト / 遅延 / フォールバック | — | 要評価 | 工学的コストは見合うか |

セルに具体的な数値を入れていないのは意図的です。これらの値は、あらかじめ設計された各実験から得られるべきものであり、見栄えのよい結論を先に書いてそこに合わせるものではありません。最後の行は忘れられがちです。大規模モデルの呼び出しにはコストと遅延があり、失敗もします。そのためフォールバック経路（中立スコアに落とす、前回の結果を流用するなど）が必要で、そのオーバーヘッドも「AIあり」の勘定に入れるべきです。

センチメントを加えたことで訓練期間だけ改善し、大半のテスト期間でむしろ悪化したのであれば、そこから導く結論は「カーブをもっときれいに見せるよう調整を続ける」ことではなく、「この因子には、今のところ安定した付加価値がないかもしれない」と認めることです。

## ウォークフォワードが不完全な結果を受け入れさせてくれた

ウォークフォワードの各ウィンドウは、訓練期間とその直後のテスト期間から成ります。パラメータは訓練期間でしか選べません。テスト期間では、ロックした設定を一度だけ走らせます。最終的な成績は、各期間のアウトオブサンプルリターンをつなぎ合わせたものです。その利点は、取引の本当の情報の流れを模していることにあります。各時点で使えるのはその時点で既知のデータだけであり、未来にしか現れないパターンを借りることはできません。

ここには私も踏み抜いたことのある罠があります。テスト期間は一度しか見てはいけない、ということです。あるウィンドウの成績が悪いからといって、戻って減衰パラメータを変え、同じテストを再実行すれば、その「アウトオブサンプル」はすでに見られ、調整に使われてしまい、ひそかに訓練セットの一部になります。アウトオブサンプルが説得力を持つのは、評価されるまで戦略にとって未知のままだからです。

この手順によって、うまくいかなかったウィンドウをそのまま残そうと思うようになりました。以前の私は、それらをモデルの欠陥とみなしていたのですが、今はむしろこう問いかけます。相場環境が変わったのか、減衰期間が適切でないのか、テキストソースに偏りがあるのか、あるいはセンチメント因子にそもそも十分な経済的意味が備わっていなかったのか、と。これらの原因はまったく異なる次の一手を指し示すのであって、「モデルがダメだ」と一括りにはできません。

「8ウィンドウ中6ウィンドウがマイナス」は事実です。「モデルが十分に大きくない」は解釈に過ぎません。事実と解釈のあいだには一回の実験があります。解釈は、あらかじめ設計された次の新しい実験を待たなければならず、すでに見てしまったテストセットをあとから修正する口実にしてはならないのです。解釈を結論とみなすことは、私が最も犯しやすく、最も自己点検しにくい間違いです。

## いまの私の結論

大規模モデルがクオンツシステムの中で最も適しているのは、追跡可能な情報の整理・分類・調査の補助です。ポジションとリスク管理は、引き続き明確なルールが担うべきであり、最終的な価値は必ずアウトオブサンプルの結果とコストで検証されなければなりません。モデルを「テキストを監査可能なデータに変える」という一区画にとどめておけば、その貢献は足し引きでき、再現もできるものになります。

抑制することはAIの力を弱めることではありません。むしろ、境界がはっきりして検証可能な役割を与えることによって、はじめて「AIが実際に何をもたらしたのか」がわかるのです。

これらの手法は、[AIクオンツシステム](/quant/) の研究サイクルの中で継続的に検証を重ねています。
