越境 EC の商品選定をするとき、いちばん危うい状態は「まったく情報がない」ことではなく、「情報はたくさんあるのに出どころを説明できない」ことです。あるショート動画が急にバズったり、どこかのプラットフォームのランキングが熱そうに見えたり、サプライヤーから「このカテゴリが伸びている」と言われたり。どれにも価値はあるかもしれませんが、「いつ、どこから、どう計算したのか」に答えられなければ、安定した判断材料にはなりにくいのです。

やっかいなのは、この種の「勘」は伝わる過程でどんどん増幅されがちなことです。スクリーンショットが転送され、言い回しが単純化され、時刻が抜け落ち、最後には元がどの市場・どの日・どの価格帯だったのか誰も言えなくなります。実際に仕入れて広告を出す段になって、根拠がとっくに古びていたと気づくのです。

越境トレンドレポートプロジェクトの狙いは、そうしたバラバラな「勘」を、追跡可能で再現性のある日報に変えることです。どのおすすめもその情報源までたどれ、どの数字もその計算基準までたどれる、という状態を目指しています。

## まずは複数ソースからの収集、AI からではない

システムは Google Trends の RSS、公開 WooCommerce 商品カタログ、Frankfurter の為替レートに加え、認証情報に応じて有効になる楽天、Yahoo Shopping、Rainforest などのソースを組み合わせます。候補となる各商品には、ソースリンク、元のタイトル、画像、マーケット、通貨、収集時刻を保持します。これらのフィールドは、あとから何かを追跡するためのすべての土台です。ひとつ欠けると、そのデータは「証拠のように見えるだけ」のものになってしまいます。

ソースは形がかなり異なります。RSS のものもあれば REST のものもあり、認証やレート制限が必要なものもあります。だから収集層の最初の仕事は「適合」です。各ソースを統一された `SourceAdapter` として包み、外には「候補を一括で取る」という一つの操作だけを見せ、内部で認証、ページング、フィールドのマッピングをそれぞれ処理します。その上のスケジューリング、重複除去、換算は、特定プラットフォームのプロトコルを一切気にする必要がありません。

スケジューリングは、周期をコードに直書きするのではなく、固定頻度の動的タスクを使います。あるソースが遅くなったり一時的に止まったりしても、変えるのは設定だけで、再デプロイは要りません。重複除去は「ソース + 外部 ID + マーケット」をべき等キーにするので、同じ日に二度採れた商品は積み重ねずにマージされ、同じ品がランキングに二度出ることはありません。

収集タスクが「完全に成功したか」は、人が推測するのではなく記録されなければなりません。各タスクは監査を一件残します。開始時刻、ソース、今回の候補数、成功か失敗か、失敗理由。あるソースが今日落ちていれば、日報はそれがまだ在るふりをしません。そのソースが欠けていることを明示します。

```text
CollectionRun
  ├─ source        楽天 / Yahoo / WooCommerce ...
  ├─ startedAt     収集開始時刻
  ├─ fetched       今回取得した候補数
  ├─ status        SUCCESS | PARTIAL | FAILED
  └─ note          失敗理由 / レート制限 / 認証情報の欠如
```

Spring Boot のバックエンドが、データソースへの適合、スケジューリング、重複除去、為替換算、利益モデルを担当し、MySQL にはトレンドシグナル、商品プール、日報、マーケット設定、収集監査、管理画面の権限データを保存します。Vue のフロントエンドは、公開用の商品選定ダッシュボードと独立した管理バックエンドに分かれています。私は、システムにいつでも答えられるようにしておきたいのです。「今日のおすすめはどのソースから来ているのか」「どの為替レートを使ったのか」「送料やプラットフォーム手数料はどう計算したのか」「収集タスクはすべて正常に終わったのか」という問いにです。

## AI は標準化の層であり、データソースではない

プラットフォームが異なると、商品タイトルにはブランド、スペック、マーケティング文言、言語の違いが混ざりがちです。同じワイヤレスイヤホンでも、一方では長い宣伝文句、もう一方では型番だけ、ということが起こります。ここで DeepSeek は主にタイトルの正規化、カテゴリーへのまとめ、候補順位の説明に使い、「人気商品」をゼロからでっち上げるためではありません。加工するのは常にすでに採ってきたデータであり、データを作り出すことはありません。

大規模モデルが利用できない場合でも、ソースデータはシステムに取り込まれ、決定的な中国語カテゴリーとルールがフォールバックとして使われます。フォールバックは「使えない状態に落ちる」ことではなく、予測可能で決定的な経路に切り替えることです。キーワードを固定カテゴリーに対応させ、既知のルールで並べる。結果は安定して再現でき、ただ自然言語による仕上げがないだけです。

```text
候補を一件標準化する:
  LLM が利用可能なら:
      タイトル → 正規化タイトル、統一カテゴリー、順位の理由
  そうでなければ（タイムアウト / エラー / 未設定）:
      タイトル → キーワードルールで決定的なカテゴリーへ対応
      順位     → 既存の重みルール、モデルは呼ばない
  どちらの経路も同じ商品テーブルへ書き戻し、normalizedBy = ai | rule を付ける
```

この設計は「AI の出力がもっともらしく流暢ならデータもきっと正しい」という、ありがちな錯覚を避けるためのものです。流暢さは言語モデルの既定能力であって、データの正しさとは関係ありません。「いかにも専門的に見える」分析が、たどっていくと元の情報源など存在しなかった、という例を私は何度も見てきました。私にとって、AI の判断は必ず既知のソースに紐づいていなければなりません。モデルは整理や比較を手伝えても、収集の証拠そのものに取って代わることはできません。だから各候補には、AI とルールのどちらで標準化されたかを記録し、ずれが出たときに収集の問題か加工の問題かを切り分けられるようにしています。

## 人気ランキングより利益モデルのほうが意思決定に近い

商品が「熱い」からといって売る価値があるとは限りません。日報では、仕入れ価格、為替レート、送料、プラットフォーム手数料、決済手数料、税金、広告コストを同じ利益計算に入れ、そのうえでマーケットごとの販売価格や粗利の余地を比較します。人気は「見ている人がいるか」に答えるだけで、利益は「売って結局いくら残るか」に答えます。

完全な計算基準は、実のところ一本の引き算です。

```text
粗利   = 販売価格
       − 仕入れ価格
       − 為替換算の損益
       − 送料
       − プラットフォーム手数料
       − 決済手数料
       − 税金
       − 広告コスト
粗利率 = 粗利 / 販売価格
```

![利益ウォーターフォール：販売価格から各種コストを順に差し引いて粗利にする図](/images/cross-border-trends-profit.svg)

ウォーターフォール図にするとより直感的です。販売価格が左端の満杯のバーで、そのあと各コストが下向きの段になり、右端に残るのが粗利です。利益を本当に削るのは、いちばん目立つ仕入れ価格ではなく、重なり合ったプラットフォーム手数料・決済手数料・広告コストであることが多いのです。単体では小さくても、積み重なれば「人気商品」を赤字取引に変えるほどになります。

同じ商品を別のマーケットに置くと、この引き算の各項が変わります。販売価格は現地の相場で動き、為替は日次で決まり、プラットフォーム手数料や税金は市場のルールで異なります。だから日報は横並びの比較をします。同じ候補でも、A 市場では粗利率がある値、B 市場ではまったく違う値になりえます。

| 項目 | 市場 A（例） | 市場 B（例） |
| --- | --- | --- |
| 販売価格 | 100 | 92 |
| 仕入れ + 送料 | 52 | 52 |
| プラットフォーム + 決済 + 税 | 18 | 15 |
| 広告 | 12 | 10 |
| 粗利率 | 18% | 16% |

上の数字はあくまで例示で、「同じ品でも市場が違えば粗利構造が変わる」ことを示すためのものであり、実測結果ではありません。

このモデルはあくまで試算です。実際の返品率、保管、在庫回転率、広告オークションの結果は、数字を変え続けます。それでも、前提をあらわに設定できることは、売上ランキングだけを見るより一歩進んでいます。送料や料率を変更するたびに、過去の日報や計算基準も追えるようになっています。今日の粗利率が先週と違えば、為替が動いたのか、それとも私がどこかの料率を変えたのかをたどれます。

## 管理画面は飾りではない

管理バックエンドでは、ユーザー、ロール、メニュー、テナント、マーケット、カテゴリー、データソース、収集頻度を設定できます。これらは飾りではありません。マーケットとカテゴリーは収集範囲を決め、データソースと収集頻度は毎日何をどれだけ走らせるかを決め、ロールとメニューは誰がそれらを変えられるかを決めます。設定は挙動そのものです。頻度を一つ変えれば、翌日の日報が変わります。

本番環境では JWT ログインを有効にし、パスワードには BCrypt を使い、削除や設定変更には監査ログが残ります。なぜ削除にも痕跡を残すのか。商品選定は連続した判断だからです。誰かがこっそりデータソースを消したり料率を変えたりして、その記録がなければ、日報の変化は説明不能になります。監査の意味は誰かを取り締まることではなく、計算基準のどの変更もあとから振り返れるようにすることにあります。

## 小さなサーバー上での抑制

2 GB のサーバー上に、メッセージブローカーやコンテナオーケストレーション、追加のキャッシュサービスはあえて入れていません。その利点を知らないからではなく、今の規模ではそれらが解決する問題にまだ出会っていないからです。動的スケジューリング、べき等なタスク、小さめのコネクションプールで十分です。負荷は限られ、べき等性が再実行を安全にし、小さなプールはむしろデータベースの接続を食い尽くさずに済みます。

ブローカーを一つ入れれば、監視が必要で、故障しうる、メモリを食う部品をもう一つ抱えることになります。2 GB しかないマシンでは、そのコストは現実的です。複雑さは、解決すべき明確な問題があるときにだけ存在する価値があります。もし収集量が本当に単一マシンを潰すなら、そのときに非同期へ分割しキューを足せばよく、想像で先に設計するのではなく、実際のボトルネックのデータを根拠にできます。

## 試算であることの誠実さ

この点ははっきり言っておきたいのです。この日報が示すのは試算であって、約束ではありません。実際の返品率、保管コスト、在庫回転率、広告オークションは、私に見えないところで最終結果を変え続けます。そのどれか一つが、きれいな粗利率を地面まで引き戻しうるのです。

だから私は、「いかにも確実に見える」数字を追うより、前提をあらわに並べておくほうを選びます。送料、料率、税率、想定した広告コストは、すべてコードに埋め込まれた定数ではなく、管理画面で設定できるパラメータです。これには二つの利点があります。ひとつは、このおすすめがどんな前提の上に立っているかを誰でも見られること。もうひとつは、現実と試算がずれたとき、システム全体をひっくり返すのではなく、その特定の前提だけを直せることです。

誠実な試算は、精密な幻想よりも役に立ちます。
