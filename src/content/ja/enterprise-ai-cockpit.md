多くのRAGデモは、チャット欄から始まります。ファイルをアップロードし、質問を入力し、モデルが回答する。この流れはコンセプトの証明には向いていますが、実際に企業向けのスマートコックピットにしようとすると、チャットだけでは済まない課題がすぐに見えてきました。

知識ベースやドキュメントは永続化されているのか？ドキュメントを削除したとき、ベクトルはどう同期するのか？回答はどのチャンクを参照しているのか？上流のモデルストリーミングが途切れたときのフィードバックは？経営レポート、データソース、会話履歴をどうやって同じ権限・監査の境界で共有するのか？

これらの問いに共通するのは、いずれも「対話の外側」で起きているということです。チャット欄は入口にすぎず、実際に本番投入できるかを決めるのは、その裏にある保存・検索・イベントストリーム・縮退パスです。このプロジェクトは、そうした実運用に近い問いに答えるためのものです。機能を網羅することではなく、アップロードから回答までの一連の経路で「静かに失敗しうる」箇所を一つずつ明示することを狙っています。

## 2種類のデータベースが異なる役割を担う

MySQLは知識ベース、ドキュメントのメタデータ、データソース、レポートテンプレート、実行ログ、会話、業務設定を保存します。PostgreSQL + pgvectorは固定次元のベクトルとチャンクのメタデータを保持します。

なぜこれらを一つのDBに詰め込まないのか。2種類のデータはアクセスパターンがまったく異なるからです。業務データにはトランザクション、外部キー、条件フィルタ、ページングが必要で、これはリレーショナルDBの主戦場です。ベクトル検索が必要とするのは「あるクエリベクトルに対し、最も類似したtop-kを探す」こと、つまり近似最近傍探索です。高次元ベクトルを普通のテーブルに詰め込んで一行ずつ距離を計算するのは、遅く、保守も難しくなります。各データを適したエンジンに任せたほうが、インターフェースはむしろ整います。無理に統合すれば、結局どちらかの操作がもう一方のストレージ構造に合わせて歪み、読み書き双方の経路が足を引っ張られます。

ドキュメントのインポートは、分解できる一本の経路です。

- Apache TikaがPDF、Word、プレーンテキストなどの形式から本文を抽出し、形式差を吸収します。
- 制御可能なサイズでチャンクに分割します。たとえば1チャンク500文字、重なり50文字（数字はあくまで例示で、コーパスとembeddingモデルに応じて調整します）。重なりは、文の途中で切ってしまい文脈を失うのを避けるためです。
- 各チャンクからembeddingを生成します。
- ベクトルをチャンクのメタデータ（どのドキュメントの、何番目のチャンクで、原文のどの位置か）と一緒にベクトルテーブルへ書き込みます。

疑似コードにすると、境界がより明確になります。

```text
# インポート（index path）
text   = tika.extract(file)                   # PDF/Word/テキストの差を吸収
chunks = split(text, size=500, overlap=50)    # 数字は例示、コーパスに応じ調整
for c in chunks:
    v = embed(c.text)                         # 固定次元ベクトルを生成
    pgvector.insert(v, meta={doc_id, idx, span})
mysql.save(doc_meta)                          # 業務側にドキュメントを登録
```

メタデータが重要なのは、検索がヒットさせるのはベクトルでも、ユーザーが見たいのは「この一文はどのドキュメントのどの段落から来たのか」だからです。メタデータがなければ、類似度の結果を検証可能な引用に戻すことはできません。ベクトルそのものは浮動小数点の並びにすぎず、「似ている」ことは示せても「出典」は示せません。そして企業の現場は、まさに出典を重視します。

チャンクの大きさは調整すべきつまみであり、小さいほど良いわけでも大きいほど良いわけでもありません。細かく切りすぎると、1チャンクが担う意味が不完全になり、検索が半文をヒットさせがちです。粗く切りすぎると、1チャンクに複数の主題が混ざり、類似度が薄まって引用も不正確になります。重なりは切れ目に対する補償で、隣接チャンクに小さな境界テキストを共有させ、ちょうど切れ目に当たった重要文が両側で失われるのを防ぎます。これらの数字は最終的に実際のコーパスで試すしかなく、万能の初期値はありません。

質問時には、まずpgvectorのcosine検索を行い、最も類似したtop-kのチャンクをコンテキストとして取り出します。

```text
# クエリ（query path）
q    = embed(question)
hits = pgvector.search(q, top_k=5)            # 優先：cosine top-k（top_k の値は示意）
if vector_unavailable or not hits:
    hits = mysql.keyword_cjk_search(question) # フォールバック：keyword / CJK
context = [h.chunk for h in hits]             # 引用付きでコンテキストを組み立て
```

ここには省かなかった縮退パスがあります。ベクトルサービスが利用できない場合——接続失敗、タイムアウト、次元不一致——検索はMySQLのキーワード検索とCJK検索へフォールバックします。CJKの分かち書きは英語とは異なり、空白で区切ると中国語の一文を丸ごと一語として扱ってしまうため、フォールバック側はCJKを専用に扱ってはじめて意味を持ちます。フォールバックの品質は通常ベクトル検索に劣りますが、「ベクトルストアが落ちたら問い合わせ全体が不能になる」ことを防ぎます。縮退は既定の経路ではなく、明示的な最終手段です。通常はそこに到達せず、到達した際にもユーザーは少なくともキーワードベースの回答を得られ、回り続ける空白ページを見ずに済みます。

top-kのkも抑制が必要です。少なすぎれば本当に関連するチャンクを取りこぼし、多すぎれば無関係な内容がコンテキストを占有してモデルの注意を薄めます。これはチャンクサイズと連動しており、チャンクが小さいほど十分な文脈を集めるにはkを大きくする必要があります。

2種類のストアの役割は、並べて見るとより明確になります。

| 観点 | MySQL | PostgreSQL + pgvector |
| --- | --- | --- |
| 何を保存するか | 知識ベース、ドキュメントのメタデータ、データソース、レポートテンプレート、実行ログ、会話、業務設定 | 固定次元ベクトル、チャンクのメタデータ |
| アクセスパターン | トランザクション、条件フィルタ、ページング、外部キー結合 | top-k 近似最近傍検索 |
| 主な用途 | 業務ワークフローの状態を担う | 意味的検索を支える |
| 問い合わせでの役割 | keyword / CJK フォールバック | 優先の cosine 検索 |

この分担は、データベースを積み上げるためではなく、構造化された業務データと類似度検索に適した道具をそれぞれ使い、かつ縮退パスを確保するためのものです。ゆえにドキュメント削除では両側を同時に動かす必要があります。MySQLの業務レコードを消すと同時にpgvectorの対応ベクトルとチャンクも消さなければ、検索はもう存在しないドキュメントをヒットさせ、引用は意味を失います。2つのDBをまたぐ削除には自然なトランザクション保証がないため、順序と補償を考えておく必要があります。安全な方法の一つは、まず業務レコードを削除済みとして印を付け、その後ベクトルを非同期に掃除することです。途中で失敗しても、照合ジョブが「ベクトルはあるが対応ドキュメントがない」孤立チャンクを洗い出して回収でき、検索結果に静かに残り続けることを防げます。

## ストリーミング回答は必ず本物の上流から来なければならない

バックエンドはSpring WebFluxとSpring AIを使用しています。`ChatClient`は、OpenAI互換/DeepSeekなどの上流からSSEを受け取ると、トークン、参照情報、グラフ情報、完了状態をイベントストリームとしてVueのフロントエンドへ送り続けます。

これは、完全な回答をローカルで複数の文字列に分割し、タイマーで吐き出すのとは本質的に異なります。ローカルの疑似ストリーミングは視覚効果にすぎず、初字までの遅延は結局、回答全体を生成し終えるのと同じです。本物の上流ストリームなら、モデルが最初の数トークンを吐いた瞬間にユーザーへフィードバックを返せます。その代償として、本物のストリームはもはやきれいな一本の文字列ではなく、さまざまな状態を扱う必要のあるイベント列になります。

```text
event: open           // 接続確立
event: token   × N    // 増分テキスト、逐次追記
event: citation       // ヒットした参照チャンク
event: chart          // 構造化グラフデータ
event: done           // 正常終了
event: error/timeout  // 例外分岐、明示的に締める必要あり
```

このストリームをWebFluxで受けると、`Flux`として背圧を自然に扱える利点があります。上流が一区切り生成すればそのまま下流へ押し出せ、回答全体を先にメモリへ溜め込む必要がありません。ただし非同期であるということは、エラーがもはや単純なtry/catchで受け止められる戻り値ではなく、ストリーム上のイベントであり、ストリームの意味論の中で明示的にモデル化しなければならないということでもあります。

肝心なのは最後の2行です。接続は途中で切れることがあり、上流はタイムアウトすることも、エラーイベントを返すこともあります。これらを握りつぶすことはできません——フロントエンドはストリームが正常終了したのか異常中断したのかを知る必要があり、さもなければ画面は永遠に「入力中」で止まります。そのためバックエンドは、あらゆるSSEについて`done`で締めるか`error`/`timeout`で締めるかを保証し、「音もなく切れた」という第三の状態を存在させません。この不変条件は些細に見えて、ストリーミング体験を信頼できるかどうかの土台です。「終端状態のないストリーム」を一度でも許せば、フロントエンドは各所にタイムアウト推測を継ぎ足して補うほかなくなり、複雑さがすぐに跳ね返ってきます。

もう一つ見落としやすい箇所があります。NginxではSSEバッファリングを無効にする必要があります。既定ではリバースプロキシは応答をバッファリングし、ある程度ためてから転送します。これは通常のエンドポイントには最適化でも、SSEには災いです——バックエンドは逐次出力しているのに、ブラウザには最後にまとめて届き、ストリーミング体験が失われます。バッファリングを切ってはじめて、イベントは生成された瞬間にプロキシを通り抜けます。この問題の厄介なところは、ローカル直結では完璧に動き、プロキシの背後に置いてはじめて再現することで、バックエンドがそもそもストリーミングしていないと誤読しがちです。

![SSEイベントストリームの時系列：上流からChatClientを経てフロントエンドへ、error・timeout分岐を含む](/images/enterprise-ai-cockpit-sse.svg)

フロントエンドは回答テキスト、参照ドキュメント、EChartsグラフを同じコンテキストに配置します。tokenイベントは本文を追記し続け、citationイベントはヒットしたチャンクを展開可能な出典として描画し、chartイベントは構造化データをEChartsに渡して描かせます。ユーザーは「モデルが何と言ったか」だけでなく、「それを何に基づいて言ったのか」をさらに追及できるのです。

## 一度の問い合わせの完全な軌跡

これまでの要素をつなぐと、一度の問い合わせは実際に経路全体を通り抜けています。ユーザーがコックピットで問うと、質問はまずembeddingでクエリベクトルになり、pgvectorのcosine検索でtop-kのチャンクを取り出します。その瞬間にベクトルサービスが使えなければ、キーワード検索とCJK検索へフォールバックします。ヒットしたチャンクは質問とともにコンテキストへ組み立てられ、`ChatClient`が上流へ送ります。上流がトークンを吐き始めると、バックエンドはtokenイベントを転送しつつ、適切なタイミングでcitationとchartのイベントを補い、最後に`done`で締めます——途中のどの段階で失敗しても、`error`/`timeout`で明示的に締めます。

この軌跡の一歩ごとを追跡可能にしたのは意図的です。企業の現場で本当に厄介なのは、しばしば「回答が正しいか」ではなく「間違ったときにどこで間違ったかを追えるか」だからです。検索が何をヒットさせ、どの段落を引用し、ストリームが正常に終わったか中断したか——それらがログとイベントに残っていれば、不本意な回答も検証でき、「そう言ったから」で終わる問い直せない一言にはなりません。

## 企業コックピットは万能ロボットではない

現在のシステムには、レポートテンプレート、実行ログ、データソーステスト、音声インターフェース、MCP天気サンプルも含まれています。これらの機能の意味は、AIが既存のワークフローにどう入り込むかを検証することであり、すべての機能を対話ボックスに押し込むことではありません。

私が理解する「コックピット」とは、AIはその中の一つの計器であって、すべての計器を置き換えるブラックボックスではない、ということです。レポートにはテンプレートと実行ログがあり、データソースは個別に疎通テストでき、会話には遡れる履歴がある——これらはAIの出力を追跡し、レビューできるようにする構造であって、「聞けばいい」で済ませるものではありません。ダッシュボードの価値は、各計器がそれぞれの役割を持ち、読み値を突き合わせられる点にこそあります。すべてを一つのチャット欄に押し込むのは、いくつもの読み値を一文に練り込むようなもので、見栄えは良くても検証できません。

私は意図的にいくつかの境界を残しています。

- ローカルembeddingは再現可能なパイプライン検証にのみ使い、本番品質には本物のモデルが必要です。
- データソース抽出やレポートタスクにはまだMVPの要素があります。
- 公開デモでは閲覧画面を公開し、チャット、アップロード、削除、レポート実行はバックエンドの短期操作トークンで保護しています。アプリケーションレベルのRBAC、テナント分離、監査は今後の課題です。
- モデルの回答は必ず参照を含み、流暢な表現を事実の保証としては扱いません。

これらの境界を書き留めるのは、デモが実際の成熟度より立派に見えてほしくないからです。ローカルembeddingで経路が通ることは、その再現品質が本番に耐えることを意味しません。閲覧専用デモに短期トークンを加えれば軽い破壊は防げますが、それが完全な権限体系になるわけではありません。「ここはまだMVPだ」と正直に示すほうが、後で見抜かれるより手間が少ないのです。

最後の一つが、私が最も重視する点です。流暢さと正しさは別物です。出典を引用できる回答は、たとえ言い回しが平凡でも、検証できない美文よりも役に立ちます。参照を求めることは、本質的にモデルの自信に検証可能なアンカーを与えることです——断定的に語るほど、その一文がどの原文から来たのかを示せるべきなのです。

## 小さなサーバーでの取捨選択

このシステムは、他の2つのプロジェクトと合計2GBのメモリを共有しています。フロントエンドはすべてローカルで静的ファイルにビルドしてあり、サーバーでは制限付きのJVMバックエンドだけが動いています。データベース接続プール、Quartzスレッド、ヒープ、メタスペース、ダイレクトメモリは、すべて明確な上限を設定しています。

なぜ一つ一つに上限を固定するのか。共有メモリのマシンで最も危険なのは、あるコンポーネントが多く使うことではなく、上限を持たないことだからです。境界のない接続プールやスレッドプールは、負荷の下で静かにメモリを食い尽くし、同じマシン上の他サービスを巻き添えにします。各項目に明確な天井を設けることは、「最大でもこれだけ使う」と前もって宣言することであり、キャパシティを予測可能にします。予測可能であることは「速く動く」ことより重要です——このマシンでは、制御されないメモリスパイクが引き起こす連鎖障害の代償は、節約できるわずかな遅延をはるかに上回ります。

ダイレクトメモリはとくに個別に見張る価値があります。WebFluxのようなNettyベースのフレームワークはヒープ外メモリを使い、これは通常のヒープ上限に縛られず、設定時に最も見落とされやすい箇所です。トラフィックが増えると、ヒープには余裕があるように見えてもヒープ外は静かに膨らんでいることがあります。これも明確な上限に含めてはじめて、このマシンのメモリ勘定を本当に締められます。

もし全体のリソースが継続的にしきい値を超えた場合、スマートコックピットは真っ先に一時停止されるバックエンドになります。これは意図的な優先順位づけです。他の2つのプロジェクトに比べると実験場の性格が強く、止めても代償が最も小さいからです。それは失敗ではなく、キャパシティの境界の一部です。システムは、いつ自制すべきかを知っているべきなのです。「誰が先に道を譲るか」を前もって決めておくほうが、メモリが逼迫してから即興で選ぶよりずっと堅実です。

現在のバージョンは [/smartCockpit/](/smartCockpit/) で開くことができます。ここはまだ実験室ですが、もはや単なるチャット欄ではありません。
