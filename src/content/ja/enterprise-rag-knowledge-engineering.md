企業向け知識ベースには分かりやすい錯覚があります。文書をベクトル化し、チャット欄が流暢な文章を返せば、RAGは完成したように見えます。しかし実際の失敗の多くは、モデルがコンテキストを見る前に起きます。解析時に見出しが消える、表が平文化される、契約番号が候補に入らない、旧規程が最新版より上に並ぶ、あるいは「その規則は誰に適用される？」という追質問が主語のない新規質問として検索される、といった問題です。

そこで[企業AIコックピット](/smartCockpit/)の知識経路を改修しました。目的はより大きなモデルへの交換ではなく、「なぜこの証拠がモデルへ渡ったのか」を観測・テスト・改善できる状態にすることです。

## RAGは二つの生産ラインである

RAGはインデックス経路とクエリ経路の合成です。

```text
index: file -> parsing/structure recovery -> chunking -> provenance -> embedding -> index
query: question -> query understanding -> permission/time filters -> dense + keyword -> rerank -> context -> answer + citations
```

どちらの経路でも情報は失われます。見出し階層が消えれば、優れたembeddingでも業務文脈を失った一文しか表現できません。有効期限を無視すれば、高精度な類似検索ほど自信をもって古い規程を返します。したがって調査順序は、抽出結果、正解候補の召回、フィルタと融合、版の競合、最後にモデルの証拠利用、となります。

## チャンクは文字列ではなく最小の業務文脈

従来は固定文字数の窓で分割していました。予測しやすい反面、見出しと本文を離したり、文の途中で切ったりします。新しい処理はMarkdown見出し、中国語の章見出し、番号付き節、段落、文末境界を先に認識し、それでも大きすぎる構造単位だけを文字窓へフォールバックします。

各チャンクは所属節を保持します。

```text
節：返金承認規則
返金申請は受領後7日以内に、注文番号を添えて提出する。
```

隣接チャンクには限定的な重なりを残し、登録前に完全重複を指紋で除去します。検索後、同じ文書の隣接チャンクがともに高得点なら原順序で結合し、重複部分を削ります。これにより、細かすぎて意味が切れる問題と、重複チャンクがコンテキストを埋める問題を同時に抑えます。

登録時には `source`、`sourceType`、`parser`、`ingestedAt`、`contentHash`、`chunkStrategy` も保存します。これらは文章表現を直接改善しませんが、証拠の出所、解析器、内容変更、索引戦略を追跡可能にします。索引再構築後に品質が変化したとき、provenanceがなければ原因調査は推測になります。

## Dense検索とキーワード検索は補完関係

embeddingは異なる表現の同じ意味を見つけるのが得意です。キーワード検索は契約ID、SKU、エラーコード、版番号、固有名詞に強みがあります。企業質問には両方の信号が含まれます。ベクトルだけでは `CN-2026-0818` が一般的な契約規程に負け、キーワードだけでは「退職後も精算できるか」が「雇用関係終了後の費用処理」という節を逃すことがあります。

現在は二つの候補集合を同時に取得します。

```text
dense   = pgvector.cosine(query, candidate_k)
lexical = mysql.keyword_cjk(query, identifiers, candidate_k)
fused   = reciprocal_rank_fusion(dense, lexical)
ranked  = exact_phrase_identifier_version_freshness_boost(fused)
context = merge_adjacent(dedupe(ranked), top_k)
```

Reciprocal Rank Fusionは、cosine値と語彙スコアを無理に比較せず順位を融合します。その後、完全一致、業務ID、タイトル一致、新しい版、最近の登録に限定的な加点を行います。手作業の規則が関連度を乗っ取らないよう、これは小さな補正に留めます。

二経路は縮退性も高めます。ベクトル接続が一時的に失敗しても語彙候補が残り、語彙側が停止してもdense候補が働きます。ハイブリッド検索は平均品質だけでなく経路の耐障害性も改善します。

## 最新知識には明示的なライフサイクルが必要

空の知識ベースより危険なのは、権威がありそうな三つの版が互いに矛盾している知識ベースです。類似度だけでは、下書き、廃止、期限切れ、翌月発効を理解しません。

検索層は次のmetadataを扱うようになりました。

| フィールド | 通常検索での扱い |
| --- | --- |
| `status` | active、published、currentなどを対象にする |
| `effectiveFrom` | 未発効の規程を除外する |
| `effectiveTo` | 期限切れ知識を除外する |
| `supersededBy` | 新文書で置換された版を除外する |
| `version` | 関連度が近い候補では新しい版を少し優先する |

管理者は診断時に無効知識を含められますが、通常ユーザーへ版の判断を押し付けるべきではありません。次の運用課題は、新版公開時の旧版置換と、期限切れ文書・孤立ベクトルの定期照合です。知識更新は検索アルゴリズムと同じくらい重要です。

## 追質問には検索用の文脈補完が要る

チャットモデルは「その規則」を理解しても、retrieverが見るのは現在の文字列だけです。「返金期限は？」の次に「その規則は誰に適用？」と聞くと、後者単独のembeddingは弱くなります。

明確な指示語を含む追質問では、直前のユーザー質問を検索クエリへ追加します。生成側には元の質問を維持します。

```text
返金期限は？
追質問：その規則は誰に適用される？
```

すべての質問をモデルに書き換えさせない保守的な設計です。実データの評価集合が整った後、小型モデルによる構造化query rewriteを導入し、元クエリとの `Recall@k` を比較できます。

## MCP Toolと知識ベースの役割を分ける

知識ベースは安定し引用可能な事実、MCP Toolは天気、地図、計算、業務照会など実行や現在状態が必要な能力に向きます。古い天気を文書として答えたり、制度条文を毎回ライブ呼び出しで読むべきではありません。

モデルが計画できるのは、画面で明示的に選択されたツールだけになりました。「ツール有効、選択なし」は権限なしを意味し、暗黙の天気ツールは付与されません。ホストはMCP schemaで引数を検証し、実行段数を制限し、observationと軌跡を記録します。

```text
user selection -> tool catalog/schema -> model plan -> host validation/execution -> observations -> answer
```

これは単なるfunction callingと、監査できるツール経路の違いです。

## Retrieval Labで調整ループを閉じる

以前は検索結果が最終回答の背後に隠れていました。回答が悪いと、召回が誤ったのか、正しい証拠をモデルが誤用したのかをログから推測していました。知識ベース画面にはRetrieval Labを追加し、実際のHybrid + RRF順位、スコア、要約、完全な証拠を直接確認できます。保護されたAPIは本番検索経路を再利用し、別のテスト用アルゴリズムを持ちません。

次は小さくても実際的なgolden setを維持します。許可された知識ベース、期待文書または段落、重要事実、ツール呼び出しの要否を記録し、変更ごとに以下を比較します。

- `Recall@k`：正しい証拠が候補へ入ったか。
- `MRR`：最初の正解が十分上位か。
- 引用正確性：主張を引用部分が直接支えるか。
- 期限切れ・競合知識の混入率。
- p50/p95遅延と候補数。

「証拠なし」も測る必要があります。無関係なチャンクから流暢な回答を作るより、正直な空結果のほうが有用です。Retrieval Labは空結果の際、top-kをすぐ増やすのではなく、状態、有効期日、metadata、分割内容の確認を促します。

## 実践から得た結論

企業RAGの中心資産はベクトルDBそのものではなく、知識を生産し、検索失敗から学べる保守可能なシステムです。モデル改善は推論と表現を高めますが、壊れた解析、欠けた権限境界、期限切れ規程、悪い候補集合を自動修復しません。

実装順序は次のように考えるようになりました。

1. 構造、出所、ライフサイクルを追跡可能にする。
2. 意味検索と語彙検索を組み合わせ、候補過程を可視化する。
3. 実際の質問から回帰指標を作る。
4. その後にembedding、reranker、生成モデルを比較する。

この順序なら、改善がどの層で起きたかを説明でき、退化の原因も絞れます。現在の実装とRetrieval Labは[企業AIコックピット](/smartCockpit/)で確認できます。
