同じシステムを複数の工場へ別々にリリースする——これは私が数々の実プロジェクトで磨いてきたことです。同じ Java + Vue のコードベースを別々の現場へ落とし込む必要があり、どの工場も固有のデプロイブランチを持ち、機器のアドレス、ライン構成、データベーススクリプトはそれぞれ違います。それでも機能は大きく共通です。ある工場で磨き上げたログ基盤は、たいてい工場 B や工場 C も欲しがります。

問題はすべて「欲しがる」という一語に潜んでいます。機能をある工場から別の工場へ移すとき、いちばん横着なやり方はブランチをマージしてしまうことで、それこそが地雷を埋める手なのです。この記事は、私が最終的にたどり着いた規律についてです。拠点間で機能を再利用するなら、`cherry-pick`（コード選別）を一本道だけ通す。

## まず、三種類のブランチの役割を分ける

手を付ける前に、このリポジトリのブランチが対等ではないことを認めなければなりません。三種類あります。

- **主幹 `prod_main`**：どの工場も共有できる、きれいな機能コミットを収める場所。特定の現場には対応せず、共有作業の集散地です。
- **デプロイブランチ `prod_factory_a`、`prod_factory_b`……**：各工場が現場で実際に動かすもので、それぞれ固有の設定を抱えています。
- **廃止された根ブランチ**（かつての `main` や `prod` など）：開発・選別・リリースの基準線ではなくなり、履歴として残っているだけです。

ひとつ、専用の一文で書いておく落とし穴があります。デプロイブランチの中には名前に `main` を含むもの（ある工場の `factory_c/main` など）があります。それは根ブランチ**ではなく**、主幹**でもなく**、単にその工場のデプロイブランチです。名前は誤解を招きますが、役割は誤りません。

ワークフロー全体を一行で言えば——**拠点をまたぐ機能は一本道だけを通る：ソースのデプロイブランチ →（主幹の上で一つのコミットに収れん）→ 対象のデプロイブランチ。**

## 唯一のルール：デプロイブランチ同士をマージしない

いちばん直感的で、いちばん危険な手は、機能を仕上げたブランチをそのまま対象拠点へマージすることです。

```
# アンチパターン、やってはいけない
git switch prod_factory_b
git merge origin/prod_factory_a
```

これをやった瞬間、工場 A の機器呼び出し、拠点固有の設定、初期化スクリプトが、本当に欲しかった一つの機能と一緒に工場 B へ流れ込みます。その場ではビルドが通り、問題はたいてい数週間後、現場で表面化します——ハードコードされた機器アドレスがこっそり紛れ込んでいた、というふうに。デプロイブランチが表しているのは「この工場が今まさに動かしている姿」であり、そうしたブランチ同士はマージすべきではありません。

正しい道は二段階です。まずソース工場のコミットを選別・ふるい分け・収れんして主幹の上に一つのきれいなコミットにし、次に対象工場がその一つのコミットを取り込みます。

![二段階の流れ：ソースのデプロイブランチ →（cherry-pick -n で複数コミット＋ふるい分け）→ prod_main の一つのきれいなコミット →（cherry-pick -x）→ 対象のデプロイブランチ](/images/cherry-pick-flow.svg)

## 一つの機能に、主幹の上で一つのコミットだけ

機能はソース工場では、たいてい断片的に育っています。まずモジュールを作り、Service と Mapper を足し、Controller を調整し、ついでに設定をいじり、そこにその工場専用の呼び出しまで混ざっている。このコミット履歴を丸ごと持ち込んでも意味がなく、再利用もできません。

だから主幹に入れるときは、履歴ではなく結果だけを運びます。

```
git switch prod_main
git cherry-pick -n <ソースコミット1> <ソースコミット2> <ソースコミット3>
```

`-n` は `--no-commit` です。変更をすべて作業ツリーに広げつつ、急いでコミットせず、「このうち本当に残すのはどれか」という判断を私の手に戻してくれます。ここからが本当に時間のかかる工程です。ファイルごとに diff を読み、拠点固有のものを差し戻し、いらないディレクトリを削り、依存の記述を最小限の配線だけに整える。ふるい終えてビルドとテストが通ってはじめて、一つのコミットにまとめます。

```
git commit -m "feat(common): add log platform"
```

ここまで来れば、その機能は主幹の上にただ一つのきれいなコミットハッシュを持ちます。見返りは具体的です。ブランチの数は膨れ上がらなくなり、どの工場がいつ採用したかは主幹の履歴をたどればわかり、ロールバックもそのコミット一つを戻すだけです。

## 第一段階：工場 A から主幹へ

始める前に、私には 30 秒の習慣があります。`git status` で作業ツリーがきれいなことを確認し、`git fetch origin --prune` でリモートを更新し、根ブランチではなく `prod_main` に立っていることを確認し、最後に**今の `prod_main` の SHA を控える**——ロールバック地点として。

そして主幹に切り替えて更新します。

```
git fetch origin --prune
git switch prod_main
git pull --ff-only origin prod_main
```

ソースブランチで、どのコミットを運ぶのかを正確に見極めます。コミットのタイトルで判断せず、ファイル一覧と diff を読むこと。

```
git log origin/prod_factory_a --oneline --decorate
git show --stat <ソースコミット>
```

三つを確認します。これらのコミットがどのファイルを触ったか、拠点固有の機器アドレスやインターフェースが紛れていないか、コミット同士に前後の依存があるか。そこがはっきりしたら、順番に `cherry-pick -n` ですべて作業ツリーへ入れ、ふるい分けます——ここは GUI の diff がいちばん楽です。再利用できるものを残し、拠点固有のファイルを差し戻し、来てはいけない新規ディレクトリを削り、POM には必要なモジュール宣言と依存だけを残す。ビルドとテストを回し、作業ツリーにこの機能に必要なものだけが残っていることを確認したら、その**一つ**のコミットにまとめて push します。

## 第二段階：工場 B が主幹から取り込む

第二段階はずっと軽い。主幹の上にはすでに、ふるい分けとテストを経たきれいなコミットがあるからです。

```
git switch prod_factory_b
git pull --ff-only origin prod_factory_b
git cherry-pick -x <主幹の機能コミットSHA>
```

`-x` は新しいコミットのメッセージに元のコミットハッシュを書き込むので、機能の出所が一目でわかります。工場 B に追加の調整が必要なら、**それは別のコミットにします**——主幹の共通コミットに混ぜ戻すことは決してしません。ビルドしてテストし、それから push します。

## 完全な事例：ログ基盤を工場 B へ移す

抽象論はどうも空虚なので、実際にやった例を挙げます（内容は伏せてあります）。

工場 A が現場でログ基盤を作り、いま工場 B もそれを欲しがっています。関連する変更はソースブランチの三つのコミットに散らばっています。

| ソースコミット（例） | 内容 | なぜ一つずつ持ち込めないか |
|---|---|---|
| `a1c9f0e` | ログ管理を独立モジュールに統合 | 同時に複数の旧モジュールファイルを移動し、複数の POM を変更 |
| `b2d47a1` | モジュールの中核を構築 | 未完成の starter と工場 A 固有の呼び出しが混在 |
| `c3e8b90` | Service・Mapper・エンティティをモジュールへ移設 | 同時にスレッドプール、現場サービス、旧モジュールファイルを変更 |

だから先に `-n` でまとめ、それからふるい分けます。何を主幹に入れ、何を断固として外すか、あらかじめリスト化しておきます。

![事例のふるい分け：prod_main に入るのはログモジュールと最小の POM 配線、外すのは独立 starter・工場固有の呼び出し・周辺変更・フロントエンドスクリプト](/images/cherry-pick-selection.svg)

**`prod_main` に入れてよいもの**：モジュールディレクトリ `log-platform/**`、その二つのバックエンド Controller、モジュールの設定クラス、そして三つの POM にまたがる最小限のモジュール宣言と依存の配線。

**断固として外すもの**：独立した `log-platform-starter` モジュール（およびルート POM 内のその `<module>` 宣言）、工場 A の作業指示と機器呼び出し、スレッドプールのような未承認の周辺変更、そしてフロントエンドのページとデータベース初期化スクリプト。

第一段階——三つのコミットを主幹にまとめ、ふるい分け、ビルドし、一つのコミットにまとめます。

```
git switch prod_main
git pull --ff-only origin prod_main
git cherry-pick -n a1c9f0e b2d47a1 c3e8b90
git restore --staged .
# IDE で：ホワイトリスト外のファイルを差し戻し、余分なディレクトリを削り、POM を最小配線に整える
git status --short          # ホワイトリスト内容だけが残っていることを確認
mvn -pl log-platform -am clean test
git add log-platform
git add -p pom.xml          # 必要な POM の断片だけを取る
git commit -m "feat(common): add log platform"
git push origin prod_main
```

生成された SHA を控えます——それがログ基盤の、主幹における唯一の共有コミットです。

第二段階——工場 B がその一つのコミットを取り込み、テストを走らせ、それから push します。

```
git switch prod_factory_b
git pull --ff-only origin prod_factory_b
git cherry-pick -x <上記の主幹SHA>
mvn -pl log-platform -am clean test
git push origin prod_factory_b
```

三つのブランチはあるべき場所に収まります。工場 A は元のコミットと調整を保持し、主幹にはきれいなログ基盤コミットが一つ増え、工場 B のブランチはその一つのコミットを取り込み、必要なら自分の調整コミットを加える。あとで工場 C が欲しがっても、主幹から同じ一つのコミットを取り込むだけです。

## 衝突とロールバック

`cherry-pick` が衝突するのは日常茶飯事です。解決して `git add` し、`git cherry-pick --continue` で続行。取り込みを丸ごとやめるなら `git cherry-pick --abort` できれいな状態に戻ります。

失敗の巻き戻しは二通りに分かれます。**まだ push していない**：`git reset --hard <最初に控えた SHA>` で戻し、`git clean -nd` でプレビューし、確信できたら `git clean -fd` で余分なファイルを消す——だからこそ私は着手前に必ず SHA を控えます。**すでに主幹へ push した**：強制 push も共有履歴の書き換えもせず、`git revert <誤ったコミット>` で素直に打ち消しコミットを作る。他の工場がすでにその誤ったコミットを取り込んでいたら、それぞれの側でも revert します。

## コミットメッセージも追跡可能に

コミットメッセージは用途で分類し、主幹の履歴がそれ自体で説明になるようにします。共有機能は `feat(common): ...`、ある工場の調整は `feat(factory-b): ...`、共有の修正は `fix(common): ...`。「コードを修正」「機能を調整」のような、一か月後には誰も解読できないメッセージはもうやめます。

## おわりに

拠点をまたぐ協働でいちばん高くつくのは、機能を書くことではありません。何か月も経ってから、なぜこのコードがこの工場にあるのかを説明できなくなることです。うまく使えば、`cherry-pick` はひとつの規律です。共有機能を、主幹の上のきれいで追跡可能な、コマンド一つで打ち消せるコミット一つに保つこと——それはつまり、未来の自分からその説明のコストを取り除いてあげることなのです。
