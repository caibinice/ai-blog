同じシステムを複数の工場へ別々にリリースする——これは私が実際のプロジェクトで何度か踏んできた種類の落とし穴です。どの現場にも固有のデプロイブランチがあり、機器のアドレス、ライン構成、データベーススクリプトはそれぞれ違います。それでも多くの機能は共通です。ある工場で磨き上げたログ基盤は、たいてい他の工場も欲しがります。厄介さは、この「欲しがる」という一語のなかに潜んでいます。

## デプロイブランチ同士をマージしてはいけない

いちばん直感的なやり方は、機能を仕上げたブランチを対象拠点へそのままマージすることです。

```
git switch prod_factory_b
git merge origin/prod_factory_a
```

これをやった瞬間、工場 A の機器呼び出し、拠点固有の設定、初期化スクリプトが、本当に欲しかった一つの機能と一緒に工場 B へ流れ込みます。その場ではビルドが通ってしまい、問題はたいてい数週間後、現場で表面化します——ハードコードされたアドレスがこっそり紛れ込んでいた、というふうに。デプロイブランチが表しているのは「この工場が今まさに動かしている姿」であり、そうしたブランチ同士がマージし合ってはいけません。

その後、自分に課したルールはただ一つです。拠点をまたぐ機能は一本の道しか通らない——ソース拠点のブランチ → 主幹の上の一つのコミット → 対象拠点のブランチ。途中に一時ブランチは作りません。主幹（私は `prod_main` と呼んでいます）の上のあのきれいなコミットが、唯一の受け渡し単位です。

## 機能を主幹の上で一つのコミットに収れんさせる

機能はソース拠点では、たいてい断片的に育っています。まずモジュールを作り、Service を足し、Controller を調整し、ついでに設定をいじり、そこにその工場専用の呼び出しまで混ざっている。この履歴を丸ごと持ち込む意味はありません。私は必要なコミットをまず作業ツリーへ取り込みますが、コミットはまだしません。

```
git switch prod_main
git cherry-pick -n <コミット1> <コミット2> <コミット3>
```

`-n` は `--no-commit` の略です。変更を作業ツリーに広げつつ、「本当に入れるのか」という判断を私の手に戻してくれます。ここからが本当に時間のかかる工程です。ファイルごとに diff を読み、拠点固有のものを差し戻し、いらないディレクトリを削り、依存の記述を最小限の配線だけに整える。ふるい終えてビルドとテストが通ったら、一つのコミットにまとめます。

```
git commit -m "feat(common): add log platform"
```

ここまで来れば、その機能は主幹の上にただ一つのきれいなコミットハッシュを持ちます。

## 他の工場は、そのコミット一つを取り込むだけ

使いたい拠点は、主幹からそのコミットを一つ持っていきます。

```
git switch prod_factory_b
git cherry-pick -x <主幹コミットのSHA>
```

`-x` は新しいコミットに元のコミットハッシュを記録してくれるので、あとから出所をたどれます。対象拠点で追加の調整が必要なら、それは別のコミットとして入れます。調整を主幹の共通コミットに混ぜ戻すことは、決してしません。

このやり方が本当に私を楽にしてくれるのは、優雅さではなく、複雑さを押さえ込んでくれる点です。ブランチの数は膨れ上がらなくなり、どの共通機能も一目でわかるコミットに対応し、どの工場がいつ採用したかは履歴をたどればわかります。ロールバックも、そのコミット一つを戻すだけです。

## うまくいかなかったとき

まだ push していないなら、`git reset --hard` で作業前に控えておいた SHA へ戻します——だからこそ私は着手前に必ず一つ控えておきます。すでに主幹へ push してしまったら、強制 push も共有履歴の書き換えもせず、`git revert` で素直に打ち消しコミットを作ります。他の工場がすでにその誤ったコミットを取り込んでいたら、それぞれの側でも revert します。

拠点をまたぐ協働でいちばん高くつくのは、機能を書くことではありません。何か月も経ってから、なぜこのコードがこの工場にあるのかを説明できなくなることです。一つの機能に一つのコミットだけを残すのは、つまるところ、未来の自分からその説明のコストを取り除いてあげることなのです。
