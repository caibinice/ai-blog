今回の共有を準備していて、自分が話題を「どのフレームワークを使ったか」に語りがちだと気づいた。Spring AI、RAG、MCPを一通り紹介できても、聞いた人が必ずしも分かるわけではない：なぜすでに質問に答えられるチャットボックスがあるのに、ワークフローオーケストレーションまで作るのか？

後に起点を変えた：**「注文SO20261001を調べて、いくら返金できるか見て。」**

この文は理解は難しくないが、モデルが受け取った直後には、注文が受領済みか、受領から何日経ったか、商品が使用済みかを知らない。プロンプトを長くすれば、モデルは手順を列挙できる。金額を得るには、プログラムが注文を照会し、その結果を次のステップに戻さなければならない。私のスマートコックピットにはもともと知識Q&Aとツール統合があったが、今回補ったのは、これらのステップを組織するGraphランタイムと、それがどう動くかを見られるページだ。

## まずAgentを素朴に説明する

今はAgentをこう理解するほうが好みだ：**目標を中心に、既存の情報に基づいて行動を選び、結果を得て、続けるかどうかを決めるプログラム。** モデルはその中の意思決定部品であり、プログラム全体ではない。

これは単発のモデル呼び出しに価値がないという意味ではない。材料がすでに揃っていれば、一度の呼び出しでいくつかの問題を分析し、回答を組み立てることは十分できる。オーケストレーションが必要なのは、タスクがまだ外部の事実に依存していたり、行動に前後関係があったり、実行結果が次のステップを変えたりする場合だ。

カスタマーサービスでは、こうした入力が典型的だ：

- 返品ポリシーを聞くなら、知識ベースから証拠を取る必要がある。E02故障のスクリーンショットをアップロードするなら、まず可視情報を抽出してから検索する。
- 注文がいくら返金できるか聞くなら、注文を照会して試算する必要がある。「照会を計画している」を「すでに照会した」と混同してはいけない。
- ポリシー、返金、売上レポートを同時に聞くなら、分けて処理し、それぞれの結果を持ち寄って集約する必要がある。
- 照会失敗、証拠不足、顧客が人手を要求する場合、明確な退出経路が必要だ。

ここにはあらかじめ規定されたワークフローもあれば、モデルが行動を選ぶ局所的なループもある。無理に二つの排他的な製品に分ける必要はない。AnthropicのワークフローとAgentの区別にはとても賛同する：違いは、プロセスがコードによってどこまで事前に定められているかであり、プロンプトに「あなたはインテリジェントエージェントです」と書いてあるかどうかではない。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## Graphが管理するのは状態と遷移であり、ページ上の線ではない

Graphの三つの基本概念で始めるには十分だ。

**State**は今回のタスクで既に分かっている事実を保存する。例えば顧客の質問、ヒットした知識、ツールの観察結果、現在のラウンド、回答ドラフトなどだ。**Node**は一つの具体的なことを行い、状態を読み、差分を返す。検索ノードとフォーマット整理ノードはモデルを呼び出さなくてよい。**Edge**は次にどこへ行くかを決め、固定接続でも、状態によって異なる分岐をたどることもできる。

私が最初にGraphを理解したときは、DAGと見なしがちだった。Agentの鍵はちょうど、辺が前のノードに戻ることを許す点にある：ツール結果が一度戻ってきたら、もう一度意思決定する。検索に結果がなければ、フィードバックを持ってクエリを書き換える。ループには出口と予算も同時に必要だ。

LangGraphは2024年1月の紹介で、循環可能なグラフをAgentランタイムの重要な能力としていた。コックピットはもともとJava/Springプロジェクトであり、私は同じ技術スタックでSpring AI Alibaba Graphの`StateGraph`と`CompiledGraph`を使い、このデモのためにもう一つのPythonサービスを立ち上げることはしなかった。[LangGraph 发布介绍](https://www.langchain.com/blog/langgraph)、[Spring AI Alibaba Graph 指南](https://java2ai.com/docs/frameworks/graph-core/quick-start/)

コードに落とすときには、状態フィールドのマージ方法も規定しなければならない。コックピットのこのバージョンのメイングラフは`ReplaceStrategy`を使う：ノードが新しい証拠や観察リストを返すと、対応するフィールドを置き換える。ツール結果を追加したいときは、ノードが古いリストと新しい結果を一つのリストに合成してから返す。Mapにフィールドを一つ増やせば、以降の状態が自動的に正しくマージされるわけではない。

フレームワークがこのグラフを進め、フロントエンドはイベントを観察するだけだ。ウェブページを閉じても、すでに送信された実行はアニメーションが一つ欠けたからといって止まることはない。逆に、フロントエンドが一本の線を明るく描いても、バックエンドが実際にそのノードを実行したことを意味しない。

## カスタマーサービス要件からエンタープライズアプリの骨格を描く

私のやり方は、まず分岐を決めることだった：入力を正規化し、必要なら画像観察を行い、それから意図を識別する。ポリシーと故障は検索へ、売上データはレポートMCPへ、注文はツールループへ、複合問題は専門家グラフへ、人手要求は直接引き継ぎ資料を形成する。各分岐が集めた証拠は回答とレビューのノードに戻り、必要なら修正または再検索する。

![智能座舱完整编排工作台：八个场景入口、运行历史、客服主图和节点详情](/images/cockpit-agent-overview.png)

メイングラフを広げて見ると、おおよそ以下の構造になる。ツール、専門家、検索にはいずれもループがあるが、退出条件は異なる：

```text
输入归一化 → 有图则提取图片证据 → 意图识别
  ├─ 政策或故障 → 知识检索 ─────────────────────┐
  ├─ 销售报表 → MCP 工具发现与调用 ──────────────┤
  ├─ 订单退款 → 工具决策 ⇄ 实际执行与观察 ───────┤
  ├─ 组合问题 → 拆任务 → 专家子图 ⇄ 完成检查 ────┤
  └─ 人工诉求 → 保存交接资料 → 等待人工          │
                         人工反馈 → 恢复图 → 完成│
                                               ↓
                                证据驱动回答 → 评审 → 完成
                                         ↑      │
                                  修订草稿┘      └→ 改写查询 → 再检索
```

今回コックピットに統合したのはワークベンチ全体であり、注文と専門家の二つのボタンだけを残したのではない。もともとのAgent Studioの欄は引き続き項目ごとに操作できる。ただしコックピットに入れた後、シーン欄はページ上部のコンパクトなレイアウトに変更し、常駐サイドバーを重ねないようにした。

| シーン入口 | この経路で何を検証するか |
|---|---|
| 製品知識RAG | 意図分類、実際のベクトル検索、出典付き回答とレビュー |
| 画像とテキスト | 画像証拠が先に状態に入り、分類と検索に影響する |
| 企業レポートMCP | ツールSchemaを発見し、`tools/call`を実行し、月報を読み戻す |
| ツール呼び出しループ | 注文を照会してから返金を試算し、結果が次のラウンドに影響するのを観察する |
| マルチAgent協調 | タスクを分け、三つの専門家グラフを呼び出し、進捗を確認し、集約する |
| 人手引き継ぎ | 引き継ぎ資料を保持し、人手で意見を記入してから実行を再開して復旧グラフへ |
| フィードバック駆動の再検索 | 初回の証拠が不足し、クエリを書き換えて再検索する |
| ツール異常と予算 | タイムアウトを失敗観察とし、予算が足りれば続行、尽きたら人手へ |

さらに見落とされがちな入口が三つある：**デモ知識**では検索、追加、TXT/MDのインポートができる。**共有ガイド**では重点ケースを直接読み込める。**最近の実行**では記録を再度開き、ノードを確認し、リンクをエクスポートできる。八つのシーンは同じモニタリングとリプレイを共有しており、それぞれにプリセットアニメーションを用意しているわけではない。レビューの手戻りは、入力エリアの故障オプションで個別に検証できる。

この図はすべてのエンタープライズ問題を解決してくれたわけではない。ツールが何にアクセスできるか、誰が書き込み操作を実行できるか、失敗を何回再試行するか、返金に冪等キーがあるかは、依然としてホストプログラムの責任だ。今回のデモは意図的に返金の**試算**のみを行い、引き落としや返金インターフェースは作っていない。実際に取引を実行するときには、業務認可、承認、冪等制御を補う必要がある。

繰り返し説明しやすいように、コックピットワークベンチは分離された注文、月報、知識サンプルを使う。知識検索は2048次元hashed n-gramコサイン検索であり、クラウドのセマンティックembeddingではない。また、コックピットもともとのMySQL/pgvector企業知識ベースを置き換えてはいない。MCPとHTTPは実際のプロトコル呼び出しだ。「実際の実行」と「デモデータ」を分けて明確に言うことは、ページ全体を「プロダクションレベルのインテリジェントカスタマーサービス」と総称するより有用だ。

## ツールループ：ここで五分間立ち止まって話す

![智能座舱工具循环：两个实际执行轮次，分别查订单和试算退款](/images/cockpit-agent-tool-loop.png)

この例には業務アクションが二つしかないが、閉ループを完全に示している。

`WorkflowEngine`内の重要な構造は以下の通りで、ノード登録、状態戦略、イベントラップは省略している：

```java
graph.addConditionalEdges(
    "tool_plan",
    edge_async(state -> (String) state.data().get("toolNext")),
    Map.of("execute", "tool_execute",
           "done", "draft",
           "human", "human_handoff")
);
graph.addEdge("tool_execute", "tool_plan");

CompiledGraph app = graph.compile(
    CompileConfig.builder().recursionLimit(80).build()
);
```

`tool_plan`はまず結果が揃っているかを確認し、次に業務ラウンド数を確認し、最後にモデルにツール選択を要求する。`tool_execute`は呼び出しを検証して実行し、成功または失敗を`observations`に入れ、`toolRound`を増やす。オンラインモードでは結果を`tool_call_id`で`role=tool`メッセージとして書く。意思決定ノードに戻ると、読むのは更新された状態だ。グラフの再帰制限は別の層の受け皿であり、業務上の三ラウンド予算とは等しくない。

第一ラウンドで、`tool_plan`は注文番号を受け取り、オンラインモードではネイティブの`tool_calls`を通じて`lookup_order`を提案する。Javaはツール名とパラメータを検証し、独立したサンプルサービスへHTTPリクエストを送り、「受領から三日、未使用、商品金額599元」を得る。

第二ラウンドで、注文結果はすでに`observations`に入り、`role=tool`メッセージとしてもモデルに返されている。このとき初めて`calculate_refund`を開放し、プログラムが試算を実行し、返金可能な商品金額599元、および送料は責任認定に基づく説明を返す。二種類の結果が揃うと、ホストはツールループを終了し、回答ノードへ進む。

ここで最も間違えやすいのは、モデルが出力した関数名を関数がすでに実行されたものと見なすことだ。**`tool_calls`は提案であり、HTTPの戻りが観察結果だ。** 両者の間には、ホワイトリスト、パラメータ形式、依存順序のチェックがある。`tool_call_id`も合わせなければならない。そうでなければ、次のラウンドではプロトコルコンテキストすら不完全になる可能性がある。

私は退出の責任をすべてモデルに任せてはいない：重複呼び出し、注文番号の欠落、ラウンド数の枯渇はコードが受け止める。ツールタイムアウトを一度注入すると、失敗観察は次のラウンドに入り、黙って再試行してページに緑の「成功」だけを表示することはない。予算が二ラウンドしかなく、復旧が照会と試算を完了するのに足りなければ、人手に回す。

## マルチAgent：まず境界を見て、それからモデルを数える

![智能座舱多 Agent 工作台：知识、报表、订单专家的实际子图运行](/images/cockpit-agent-multi.png)

組み合わせ問題は三つのサブタスクに分解される：ポリシー、売上レポート、注文返金。メイングラフは三つの独立してコンパイルされた専門家グラフを呼び出し、各グラフは必要なタスクと状態だけを得る。それらは同じDeepSeekモデルを使えるが、違いはタスク、コンテキスト、ツール、グラフ構造にあり、同じプロンプトに三つの名前を付け替えることではない。

現在の実装は**順序協調**だ。各専門家が戻ると、メイングラフはまだタスクがあるかを確認し、次へ進み、最後に集約する。注文専門家の内部には注文照会と試算のループもあるため、ここでは「外側のタスクループ」と「内側のツールループ」を同時に見ることができる。私はこれを並列協調とは呼んでいない：スクリーンショットで三つの専門家がすべて完了していることは、それらが同時に実行されたことを意味しない。

メイングラフのスケジューリング骨格は長くない。以下でもノード登録は省略している：

```java
graph.addEdge("multi_plan", "specialist");
graph.addEdge("specialist", "multi_review");
graph.addConditionalEdges(
    "multi_review",
    edge_async(state -> (String) state.data().get("multiNext")),
    Map.of("next", "specialist",
           "done", "draft",
           "human", "human_handoff")
);
```

本当の責務境界は`specialist`にある：`taskCursor`に基づいて現在のタスクを取り、専門家状態を構築し、すでにコンパイルされた`rag`、`report`、または`tool`グラフを選んで`invoke()`を呼び出す。専門家は現在の質問と必要な設定だけを受け取り、メイングラフのすべての履歴を直接受け取ることはない。戻った後に`agentResults`を追加し、タスクカーソルを進める。サブグラフは独立したThread IDを持つが、イベントは同じRunのTrace IDと親Spanを継承するため、同じワークベンチで外側のスケジューリングと内側のステップを検査できる。

順序実行には実際的な利点もある。最初のデモではコンテキスト境界を説明しやすく、低メモリサーバーへの並行負荷も小さい。今後並列にするかどうかは、タスクが独立しているか、状態をどうマージするか、ツールに共有リソースがあるかを見るべきであり、Agentの数が多ければよいわけではない。

## もう一度coding agentを振り返る

ここまでやってから、Codex、Claude Codeのようなcoding agentを見ると、「プロンプトがどれほどすごいか」から「実行環境がどのようにタスクを支えるか」へ注意を移しやすくなる：ファイルを読み、コードを修正し、テストを実行し、テスト結果が次のステップに影響し、必要なら進捗を保持して後続セッションが続けられるようにする。

Harnessはこの外周エンジニアリングとして理解できる：ツール、コンテキスト組織、進捗記録、検証方法、終了条件。Anthropicの長タスクharnessに関する記事は、私に非常に直接的な注意を与えてくれた：モデルの外側の環境設計が、タスクを継続的に推進できるかに影響する。[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

「行動—観察—修正」はフィードバック制御の考え方に非常に近い。私はこれをLoop Engineeringを理解するためのエンジニアリング上の類推として扱い、厳密な制御論の収束保証とは言わないし、それに基づいてすべてのフレームワークの歴史的由来を推測することもしない。

今回の共有で最後に残したいのは、一連のフレームワーク名ではなく、さらに問い続けられる入口だ：**次のステップはどの情報に基づいて決めるのか、誰がそれを実行するのか、結果はどこに置くのか、そしてどの条件で終了するのか？** この四つの問いに明確に答えられて初めて、Agentはチャットインターフェースから検査でき調整できるアプリケーションになり始める。

[智能座舱工作流页面](/smartCockpit/workflow)でまず八つのシーンを一通り歩き、それからツールループと専門家協調を重点的に再現できる。共有時は「Agent 2分、Graph 3分、客服全図2分、ツールループ5分、専門家協調4分、Coding agent 2分」で組み、本文は約18分だ。他の分岐はさらに開いて検証できる例として扱い、二十分で一行ずつ展開はしない。モニタリングとリプレイの実装は別に[次の心得](/articles/agent-node-monitoring-replay)に記した。
