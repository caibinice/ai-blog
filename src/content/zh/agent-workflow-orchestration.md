准备这次分享时，我发现自己很容易把话题讲成“用了哪些框架”。Spring AI、RAG、MCP 都能介绍一遍，听完的人却未必知道：为什么已经有一个能回答问题的聊天框，还要做工作流编排？

后来我换了一个起点：**“查一下订单 SO20261001，看还能退多少钱。”**

这句话不难理解，但模型刚收到它时，并不知道订单是否签收、签收几天、商品是否使用。把提示词写长一些，模型可以列出步骤；要得到金额，程序还是得去查订单，再把结果交回下一步。我的智能座舱原来已有知识问答和工具集成，这次补上的，是把这些步骤组织起来的 Graph 运行时，以及能看见它如何工作的页面。

## 先把 Agent 讲得朴素一点

我现在更愿意把 Agent 理解为：**一个围绕目标，依据已有信息选择行动、取得结果，再决定是否继续的程序。** 模型是里面的决策部件，不是整个程序。

这不表示单次模型调用没价值。材料已经齐全时，一次调用完全可以分析几个问题、组织一份回答。需要编排的，是任务还依赖外部事实、动作有先后关系，或者执行结果会改变下一步的情况。

客服里这几种输入就很典型：

- 问退货政策，要从知识库取证据；上传 E02 故障截图，要先提取可见信息再检索。
- 问订单能退多少钱，要查订单并试算，别把“计划查询”当成“已经查询”。
- 同时问政策、退款和销售报表，需要拆开处理，再带着各自结果汇总。
- 查询失败、证据不足或客户要求人工，需要明确的退出路径。

这里既有预先规定的工作流，也有由模型选择动作的局部循环，不必硬分成两种互斥产品。我很认同 Anthropic 对工作流与 Agent 的区分：差别在于流程由代码预定到什么程度，而不是提示词里是否写了“你是一名智能体”。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## Graph 管的是状态和流转，不是页面上的线条

Graph 的三个基本概念就够开始了。

**State** 保存这次任务已经知道的事实，例如客户问题、命中的知识、工具观察结果、当前轮次和回答草稿。**Node** 做一件具体的事，读状态、返回增量；检索节点和格式整理节点不必调用模型。**Edge** 决定下一步去哪儿，可以是固定连接，也可以根据状态走不同分支。

我最初理解 Graph 时，容易把它看成 DAG。Agent 的关键恰好是允许边回到前面的节点：一次工具结果回来之后，再做一次决策；检索没有结果时，带着反馈改写查询。循环同时也需要出口和预算。

LangGraph 在 2024 年 1 月的介绍中，就把可循环图作为 Agent runtime 的重要能力。座舱本来是 Java/Spring 工程，我选择在同一技术栈里使用 Spring AI Alibaba Graph 的 `StateGraph` 和 `CompiledGraph`，没有为这个演示再开一个 Python 服务。[LangGraph 发布介绍](https://www.langchain.com/blog/langgraph)、[Spring AI Alibaba Graph 指南](https://java2ai.com/docs/frameworks/graph-core/quick-start/)

落实到代码时，还要为状态字段规定合并方式。座舱这版主图使用 `ReplaceStrategy`：节点返回新的证据或观察列表，替换对应字段；想追加工具结果时，节点先把旧列表和新结果合成一个列表再返回。不是给 Map 增加一个字段，后续状态就自动合并对了。

框架推进这张图，前端只观察事件。即使关掉网页，已经提交的运行也不会因为少了一段动画而停住。反过来，前端把一条线画亮，也不意味着后端真的执行过这个节点。

## 从客服需求画出企业应用的骨架

我的做法是先把分支定下来：输入归一化，必要时做图片观察，然后识别意图。政策与故障走检索；销售数据走报表 MCP；订单走工具循环；组合问题走专家图；人工诉求直接形成交接资料。各分支收集的证据回到回答与评审节点，必要时修订或重检索。

![智能座舱完整编排工作台：八个场景入口、运行历史、客服主图和节点详情](/images/cockpit-agent-overview.png)

把主图摊开看，大致是下面的结构。工具、专家和检索都有回环，但退出条件不同：

```text
输入归一化 → 有图则提取图片证据 → 意图识别
  ├─ 政策或故障 → 知识检索 ─────────────────────┐
  ├─ 销售报表 → MCP 工具发现与调用 ──────────────┤
  ├─ 订单退款 → 工具决策 ⇄ 实际执行与观察 ───────┤
  ├─ 组合问题 → 拆任务 → 专家子图 ⇄ 完成检查 ────┤
  └─ 人工诉求 → 保存交接资料 → 等待人工          │
                         人工反馈 → 恢复图 → 完成│
                                               ↓
                                证据驱动回答 → 评审 → 完成
                                         ↑      │
                                  修订草稿┘      └→ 改写查询 → 再检索
```

这次合入座舱的是整套工作台，不是只留下订单和专家两个按钮。原来 Agent Studio 的栏目仍然能逐项操作，只是放进座舱后，场景栏改为页面上方的紧凑布局，避免再叠一个常驻侧边栏。

| 场景入口 | 这条路径用来验证什么 |
|---|---|
| 产品知识 RAG | 意图分类、真实向量检索、带来源的回答与评审 |
| 图片与文字 | 图片证据先进入状态，再影响分类和检索 |
| 企业报表 MCP | 发现工具 Schema，执行 `tools/call`，读回月报 |
| 工具调用循环 | 查订单后再试算退款，观察结果影响下一轮 |
| 多 Agent 协作 | 分任务、调用三个专家图、检查进度、汇总 |
| 人工接管 | 保留交接资料，人工填写意见后继续执行恢复图 |
| 反馈驱动重检索 | 首次证据缺失，改写查询后再次检索 |
| 工具异常与预算 | 超时作为失败观察；预算够则继续，耗尽则交人工 |

还有三个容易被忽略的入口：**演示知识**可以搜索、新增和导入 TXT/MD；**分享导览**可以直接加载重点案例；**最近运行**可以重新打开记录、检查节点和导出链路。八个场景共用同一套监控和回放，而不是各做一段预设动画。评审返工则可在输入区的故障选项里单独验证。

这张图没有替我解决所有企业问题。工具能访问什么、谁可以执行写操作、失败重试几次、退款有没有幂等键，都仍然是宿主程序的责任。这次演示特意只做退款**试算**，没有扣款或退款接口；真正执行交易时还要补上业务授权、审批和幂等控制。

为了方便反复讲解，座舱工作台使用隔离的订单、月报和知识样例。知识检索是 2048 维 hashed n-gram 余弦检索，不是云端语义 embedding；它也没有替换座舱原来的 MySQL/pgvector 企业知识库。MCP 和 HTTP 则是真的协议调用。把“真实执行”和“演示数据”分开说清楚，比把整个页面统称为“生产级智能客服”更有用。

## 工具循环：我会在这里停下来讲五分钟

![智能座舱工具循环：两个实际执行轮次，分别查订单和试算退款](/images/cockpit-agent-tool-loop.png)

这个例子只有两个业务动作，但完整体现了闭环。

它在 `WorkflowEngine` 里的关键结构如下，省略了节点注册、状态策略和事件包装：

```java
graph.addConditionalEdges(
    "tool_plan",
    edge_async(state -> (String) state.data().get("toolNext")),
    Map.of("execute", "tool_execute",
           "done", "draft",
           "human", "human_handoff")
);
graph.addEdge("tool_execute", "tool_plan");

CompiledGraph app = graph.compile(
    CompileConfig.builder().recursionLimit(80).build()
);
```

`tool_plan` 先检查结果是否齐全，再检查业务轮数，最后才请求模型选择工具。`tool_execute` 校验并执行调用，把成功或失败放进 `observations`，增加 `toolRound`；在线模式还把结果按 `tool_call_id` 写成 `role=tool` 消息。回到决策节点时，读到的是更新后的状态。图的递归限制是另一层兜底，不等于业务上的三轮预算。

第一轮，`tool_plan` 收到订单号，在线模式下通过原生 `tool_calls` 提议 `lookup_order`。Java 校验工具名和参数，向独立样例服务发出 HTTP 请求，得到“已签收三天、未使用、商品金额 599 元”。

第二轮，订单结果已经进入 `observations`，也以 `role=tool` 消息回给模型。此时才开放 `calculate_refund`，程序执行试算，返回可退商品金额 599 元，以及运费需要按责任认定的说明。两类结果都齐全后，宿主结束工具循环，进入回答节点。

这里最容易讲错的地方，是把模型输出的函数名当成函数已经执行。**`tool_calls` 是提议，HTTP 返回才是观察结果。** 两者之间还有白名单、参数格式和依赖顺序的检查。`tool_call_id` 也要对上，否则下一轮连协议上下文都可能不完整。

我没有把退出责任全部交给模型：重复调用、缺少订单号、轮数耗尽都由代码兜住。注入一次工具超时后，失败观察会进入下一轮，而不是悄悄重试后只给页面显示一个绿色“成功”。如果预算只有两轮，恢复不足以完成查询和试算，就转给人工。

## 多 Agent：先看边界，再数模型

![智能座舱多 Agent 工作台：知识、报表、订单专家的实际子图运行](/images/cockpit-agent-multi.png)

组合问题会拆成三个子任务：政策、销售报表和订单退款。主图调用三个独立编译的专家图，每个图只得到所需的任务和状态。它们可以使用同一个 DeepSeek 模型，区别在任务、上下文、工具和图结构，而不是给同一个提示词换三个名字。

当前实现是**顺序协作**。每个专家返回后，主图检查是否还有任务，继续下一个，最后汇总。订单专家内部还有查订单与试算的循环，所以这里能同时看到“外层任务循环”和“内层工具循环”。我没有把它称为并行协作：截图里三个专家都完成，不代表它们同时执行。

主图的调度骨架并不长，下面同样省略节点注册：

```java
graph.addEdge("multi_plan", "specialist");
graph.addEdge("specialist", "multi_review");
graph.addConditionalEdges(
    "multi_review",
    edge_async(state -> (String) state.data().get("multiNext")),
    Map.of("next", "specialist",
           "done", "draft",
           "human", "human_handoff")
);
```

真正的职责边界在 `specialist` 里：它根据 `taskCursor` 取当前任务，构造专家状态，选择已经编译的 `rag`、`report` 或 `tool` 图并调用 `invoke()`。专家只拿当前问题和必要配置，不直接拿主图全部历史；返回后追加 `agentResults`、推进任务游标。子图有独立的 Thread ID，但事件继承同一个 Run 的 Trace ID 和父 Span，才可以在同一工作台检查外层调度和内层步骤。

顺序执行也有实际好处。第一次演示更容易解释上下文边界，低内存服务器的并发压力也更小。以后是否并行，应看任务是否独立、状态如何合并，以及工具有没有共享资源，不是 Agent 数量越多越好。

## 再回头看 coding agent

做到这里，再看 Codex、Claude Code 这类 coding agent，就容易把注意力从“提示词多厉害”移到“运行环境怎样支撑任务”上：读文件、修改代码、运行测试，测试结果再影响下一步，必要时保留进度给后续会话继续。

Harness 可以理解为这套外围工程：工具、上下文组织、进度记录、验证方式和终止条件。Anthropic 关于长任务 harness 的文章给了我一个很直接的提醒：模型之外的环境设计会影响任务能否持续推进。[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

“行动—观察—修正”与反馈控制的思路很接近，我把它当成理解 Loop Engineering 的工程类比，不把它说成严格的控制论收敛保证，也不据此推断所有框架的历史来源。

这次分享最后想留下的不是一串框架名字，而是一个可以继续追问的入口：**下一步依据什么信息决定，谁执行它，结果放到哪里，又在什么条件下结束？** 这四个问题回答清楚，Agent 才开始从一个聊天接口变成能检查、能调整的应用。

可以在[智能座舱工作流页面](/smartCockpit/workflow)先走一遍八个场景，再重点复现工具循环和专家协作。分享时我按“Agent 2 分钟、Graph 3 分钟、客服全图 2 分钟、工具循环 5 分钟、专家协作 4 分钟、Coding agent 2 分钟”安排，正文约 18 分钟。其他分支作为可以继续点开验证的例子，不在二十分钟里逐行展开。监控和回放的实现另记在[下一篇心得](/articles/agent-node-monitoring-replay)。
