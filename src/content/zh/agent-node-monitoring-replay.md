工作流能返回正确答案之后，我遇到一个很实际的问题：技术分享时，听众看到“599 元可以退”，还是不知道它怎么来的。到底查了订单没有？第二轮为什么换了工具？三个专家分别拿到了什么信息？

后台日志能查，但讲解时在终端和网页之间来回切换，很快就把注意力带走了。我于是给智能座舱的 Graph 工作台加了一份结构化执行记录：实时能看到节点流转，结束后还能停在某一步看输入输出。这篇主要记实现过程里几个容易混淆的边界。

记录的对象是完整客服主图，不只包括分享时重点演示的工具循环和多 Agent。RAG、图片、报表、人工接管以及两种反馈循环，都经过同一个节点包装器，进入同一条事件序列。这样才能在同一套界面里比较“直接取到证据”和“失败后又走一轮”的区别。

## 先分清监控、回放和恢复

![智能座舱的节点图与详情面板：高亮来自实际执行事件](/images/cockpit-agent-monitor.png)

**监控**是在观察后端正在执行的任务。**回放**是在浏览已有记录，后端不会再次查订单或调用模型。**人工恢复**则是提交新信息，让后端继续执行恢复图，会产生新的事件。

页面上的“暂停回放”只停前端游标，“停止当前工作流”才请求后端取消任务。为了避免误解，详情中的“当前状态”也明确标成最新状态：它不会随着回放倒退。历史节点的输入与输出可以查看，但这版还不是完整状态 time-travel，更不是从任意节点重新执行业务。

## 先从八个入口检查记录够不够用

我验收时不是只看节点有没有变绿，而是按场景找实际发生的事：

| 场景 | 在同一份记录里核对什么 |
|---|---|
| 产品知识 RAG | `retrieve` 返回的知识来源、分数和查询；回答用了哪些证据 |
| 图片与文字 | `vision` 的图片观察是否进入下一步分类与检索上下文 |
| 企业报表 MCP | `report_mcp` 的实际报表结果，而不是模型声称“查过了” |
| 工具调用循环 | 每轮 `tool_execute` 的工具名、参数、观察结果和不同 Span |
| 多 Agent 协作 | 三个专家路径、外层父 Span、子图节点与最终汇总 |
| 人工接管 | `run.waiting`、交接资料、`run.resumed` 和 `human_reply`；前序动作不重复 |
| 反馈驱动重检索 | 两次 `retrieve` 中间确有 `requery`，查询文本确实改变 |
| 工具异常与预算 | 失败观察是否保留；三轮恢复与两轮交人工走了不同出口 |

每个场景结束后，我都重新打开历史、导出 JSON，并用同一个回放条退到零，再前进到完成节点。回放期间不会出现新的模型调用或订单请求。人工等待中的任务也可以停止，避免留下一个已经决定放弃却仍挂在等待状态的演示记录。

知识维护和分享导览是工作台入口，不是要塞进主图的两个 Agent 节点：前者负责准备可检索资料，后者负责加载输入。需要监控的是这些输入进入 Graph 后的执行事实。这个边界划清楚，页面导航、业务运行和调用追踪就不容易混在一起。

## 我最后选择记录事件，而不是远程操纵节点颜色

节点统一经过一个包装器。进入节点时记输入，结束时记返回增量和耗时，抛异常时记失败。同一套逻辑包住主图和专家图，不必在每个业务函数里重复写监控代码。

下面是裁剪后的逻辑，不是完整可复制的类：

```java
String span = newSpanId();
emit("node.started", nodeId, path, span, input);
long started = System.nanoTime();
try {
    Map<String, Object> delta = businessStep(input);
    emit("node.completed", nodeId, path, span,
         Map.of("output", delta, "durationMs", elapsed(started)));
    return delta;
} catch (Exception e) {
    emit("node.failed", nodeId, path, span, publicError(e));
    throw e;
}
```

模型请求另外记录 started/completed/failed，以及模型名、用途和 Token 用量，父 Span 指向所在节点。这里展示的是请求、公开结果和结构化决策，不是模型内部思维。图的静态定义由 `/api/workflow/graph` 提供，节点位置是预先配置的，运行事件决定哪些边经过、哪个节点已完成。

我特意保留了“状态增量”这个说法。`node.completed.output` 只表示这次节点改了哪些字段；若当成完整 State，回看时会误以为其他字段丢失。

## 循环里，节点名字不够用

工具分支两次经过 `tool_execute`，订单专家内部也会用这个名字。按 nodeId 配输入输出，迟早会把第一轮输入配给第二轮结果。

现在记录中有几个不同层次的标识：

| 字段 | 在座舱里用来区分什么 |
|---|---|
| traceId | 整次运行；本项目与 Run ID 相同 |
| nodeId | 业务节点，例如 tool_execute |
| spanId | 这一次具体执行，不是这个节点的永久 ID |
| parentSpanId | 模型请求或子节点归属于哪次外层调用 |
| path | 主图 root，或 root/toolAgent[3] 这样的专家路径 |
| seq | 同一 Run 内递增的事件序号，用于补发和去重 |

输入与输出按 **spanId + path** 配对。专家生命周期标记复用了外层 specialist 的 Span，但路径不同，配对时加上 path 就不会拿到外层整份状态。路径里的 `[3]` 是本次任务序号，不是订单专家固定排第三。

这也让我改掉了另一个习惯：直接把所有 duration 相加。外层 specialist 的耗时已经包含子图，父子一起求和会重复计算。页面端到端耗时取事件区间，节点耗时则说明一次调用或同名节点累计情况，两者口径不同。

## 从日志到 SSE，最在意的是别漏一段

每个 Run 在 `RunStore` 中保存按顺序追加的事件。`emit` 在 Run 锁内分配 seq、追加记录并通知订阅者。新订阅同样在这把锁里，先补发游标之后的历史，再加入实时订阅。

这样处理的是一个小但真实的竞态：如果补完历史后先释放锁、过一会儿才登记订阅者，中间到达的事件可能两边都没收到。

座舱原后端是 WebFlux，所以合入时没有继续使用演示项目的 MVC `SseEmitter`，而是返回 `Flux<ServerSentEvent<...>>`。协议依然很简单：

```text
id: 19
event: trace
data: {"seq":19,"type":"node.completed","nodeId":"tool_execute",...}
```

浏览器通过 `EventSource` 接收 `trace`，按 seq 去重。重连时服务端取 `after` 与 `Last-Event-ID` 中较大的值，只补发后面的事件。人工等待时没有业务事件，15 秒的无 ID 心跳保持代理连接；五分钟流结束后浏览器可以重新连接。心跳不推进执行游标。

响应还设置了 `X-Accel-Buffering: no` 和 no-cache，避免通用 Nginx 代理攒着事件不发送。这一处若没有验证，页面可能只在最终完成时突然“亮起一整条链”，看起来像实时，实际已经错过了过程。

## 回放比我最初想的简单，边界也更明确

![智能座舱停在订单专家的一次工具结果：事件游标、输入输出与调用路径](/images/cockpit-agent-replay.png)

前端始终保存接收到的完整 events。实时视图用全部事件，回放视图用数组前缀：

```ts
const visibleEvents = computed(() =>
  trackLive.value ? events.value : events.value.slice(0, cursor.value)
)
```

节点颜色、执行次数、经过的边、工具轮次和专家卡片都从 `visibleEvents` 计算。同一游标下，各处看的就是同一段记录，不需要分别安排动画定时器。

游标是**数组位置**，不是 seq。一个节点会留下边经过、started、completed 等多条事件；单步前进寻找下一个 `node.completed` 所在的位置，而不是简单把序号加一。连续播放当前按 600ms 推进一个事件，是便于讲解的速度，不是原执行时长的复刻。

回放期间 SSE 仍可收到新事件，只是不自动移动游标。点 Live 才回到最新记录。因此播放暂停既不会暂停 Graph，也不会造成后续事件丢失。专家路径筛选目前作用于时间线和详情，主图仍按 nodeId 聚合；我会在演示时把这个区别说明白。

工具超时还有一个细节：被业务代码捕获后，会返回 `toolOutcome.ok=false`。这时节点本身完成了“产生一条失败观察”的职责，所以事件是 `node.completed`，工具卡片却显示失败。只看节点绿色与否，不足以判断业务动作成功。

完整在线回归时，我还碰到一次容易误判的失败：前三轮已经完成超时重试、订单查询和 599 元试算，最后却在 `review` 节点结束了。沿着记录往后看，报错是 native thread 创建失败，不是退款工具又超时。Graph、HTTP、SSE 和 MCP 共同占用的线程触到了进程额度。最后只把座舱的额度从 90 调到 128，CPU 和内存上限保留，再重跑八个在线场景。这也提醒我，业务循环预算和运行环境的资源预算是两回事；有了节点记录，才不必把所有失败都归给模型。

## 持久化做到哪一步，就把承诺说到哪一步

根节点边界、运行结束、人工恢复和取消会保存 JSON，先写临时文件，再原子替换。生产文件放在 `shared/workflow/runs`，不跟随 release 清理，所以升级前端或 JAR 后仍能读历史。

它不是一套完整事件数据库：每次 emit 并不马上落盘，突然退出时，最后一次检查点之后的事件可能缺失。启动时把遗留 RUNNING 标为 INTERRUPTED，人工等待状态保留。恢复使用保存的应用状态进入 `HumanResumeGraph`，不是框架原生检查点支持任意位置续跑。

目前最多保留 100 条运行，API 展示最近 40 条。记录移除内部控制字段、原始图片和 api-key，但不是通用敏感信息扫描器。截图中的客户、订单和报表都是样例；以后接真实业务资料，还要单独设计字段级脱敏、访问权限和保留期限。

我最初只是想让分享更直观，最后发现这份记录对调试同样有用：能确认模型提议和实际执行是否一致，检索重试是否换了查询，失败后是不是走到了预期出口。漂亮的节点图可以稍后再做，先把执行事实和几个 ID 记对，回放才有可信的基础。
