在上一篇把智能座舱的工作流编排跑通之后，我在内部演示和联调时很快遇到了一个特别尴尬的现实问题：

当屏幕最后打印出“可退金额 599 元”时，围观的同事和业务方第一反应往往是半信半疑：
**“这结果到底是大模型自己编的，还是真去查了订单中心？”**
**“第二轮为什么突然换了个工具？”**
**“刚才多 Agent 协作里，那三个专家到底各自拿到了什么数据？”**

作为后端开发者，我们当然可以淡定地切到终端里 `tail -f` 翻日志。但一边演示一边在终端和浏览器之间反复横跳，不仅把所有人的注意力都带偏了，排查效率也极低。

于是，我决定给从 `agentDemo` 迁移合入智能座舱（[enterprise-ai-cockpit 仓库](https://github.com/caibinice/enterprise-ai-cockpit)）的工作流补上一套**结构化的执行记录与回放系统**：在页面上既能实时看到节点流水般高亮运转，事后还能拖动时间线游标，任意查看每个节点当时的输入输出。

今天这篇文章，就来拆解这套监控与回放系统背后的核心设计与实战避坑细节。

## 核心认知：监控、回放与人工恢复的清晰边界

很多人一听到“节点监控与回放”，直觉上会觉得这套东西肯定很庞大：是不是要在后端搞一套分布式链路追踪，还要在前端做复杂的状态机倒带？

其实剥开表象，整套机制的核心非常轻巧：**一份按时间顺序追加记录的执行事件列表**。

![Agent 执行事件流：实时 SSE 与历史记录汇入同一份前端事件数组，再驱动监控和回放](/images/agent-monitoring-event-flow.svg)

在系统设计之初，最关键的是把三个容易混淆的操作在概念上彻底理清：

| 操作模式 | 本质改变了什么 | 是否会推进后端业务执行 |
|---|---|---|
| **实时监控** | 接收后端 SSE 推送的新事件，实时更新前端视图 | 是。后端 Graph 正在实际运行，前端只是被动的旁路观察者 |
| **时间线回放** | 仅仅改变前端的事件截断游标（`cursor`） | **否！** 绝对不再次调用大模型、HTTP 接口或 MCP 服务 |
| **人工接管恢复** | 提交人工审核意见，驱动后端执行 `HumanResumeGraph` | 是。会唤醒挂起的任务，产生全新的业务节点与事件 |

![智能座舱的节点图与详情面板：高亮来自实际执行事件](/images/cockpit-agent-monitor.png)

理清了这个边界，交互上的很多歧义就迎刃而解了：
- 页面上的**“暂停回放”**，仅仅是清除了前端播放器的定时器，后端正在跑的任务绝不会因此停下；
- 想要真正终止执行，必须点击**“停止当前工作流”**，由前端向后端显式发送取消请求；
- 查看历史节点的输入输出是完全安全的，因为当前回放只是在回看前端缓存的历史快照，并不是在做时光倒流的“重执行（Time-travel execution）”。

## 验收依据：在八个场景中核验真实执行

为了防止监控沦为“界面上做做样子的假动画”，我直接用系统内的八个真实业务场景来做端到端验收。在同一份记录里，我们核对的是实实在在发生过的数据链路：

| 业务场景 | 在这套记录里必须核验的硬核事实 |
|---|---|
| **产品知识 RAG** | `retrieve` 节点返回的真实知识来源切片、相似度分数，以及生成草稿是否真正引用了这些证据 |
| **图片与文字理解** | `vision` 视觉节点提取出的故障码（如 E02）是否无缝合入了下一步意图分类与检索的上下文 |
| **企业报表 MCP** | 必须看到 `report_mcp` 实际调用的报表返回值，而不是模型在文本里凭空猜测的数字 |
| **工具调用循环** | 记录下每一轮 `tool_execute` 的具体工具名、输入参数、执行耗时与对应的唯一 Span |
| **多 Agent 协作** | 知识、报表、订单三个专家的独立子图路径、父子 Span 嵌套关系，以及最终由汇总节点收拢的证据 |
| **人工接管与恢复** | 任务挂起时的 `run.waiting` 事件、沉淀的交接资料，以及提交人工意见后派发的 `run.resumed` 和 `human_reply` |
| **反馈驱动重检索** | 当首次召回不足时，能清晰看到两次 `retrieve` 之间确实插入了 `requery` 改写节点，且查询词确实改变 |
| **工具异常与预算** | 工具抛出超时异常时，失败事实作为 Observation 写入状态；若预算耗尽，能清楚追踪到流转走向人工兜底出口 |

## 后端实现：统一包装器与多层次事件设计

### 别在每个业务函数里写埋点日志

很多初学者给 Graph 加监控时，习惯在每个节点方法里手动写几行 `log.info` 或者调用一个事件发布服务。这种侵入式做法不仅代码极其臃肿，而且一旦节点抛出未捕获异常，结束事件往往直接丢失。

我们的做法是在 `WorkflowEngine` 注册节点时，使用高阶函数对所有业务节点进行统一包装（`wrapped`）：

```java
// 统一包装业务节点，零侵入注入监控能力
graph.addNode("tool_plan", wrapped("tool_plan", this::toolPlan));
graph.addNode("tool_execute", wrapped("tool_execute", this::toolExecute));
```

包装层内部的核心逻辑其实非常干净利落：

```java
public <T> NodeAction<T> wrapped(String nodeId, NodeAction<T> businessStep) {
    return state -> {
        String spanId = UUID.randomUUID().toString();
        long startNs = System.nanoTime();

        // 1. 发射边经过与节点开始事件
        emit("edge.traversed", Map.of("from", state.getLastNode(), "to", nodeId));
        emit("node.started", nodeId, spanId, state.getPublicSnapshot());

        try {
            // 2. 执行真正的业务纯函数
            Map<String, Object> delta = businessStep.apply(state);
            long durationMs = (System.nanoTime() - startNs) / 1_000_000;

            // 3. 记录节点成功完成及产生的状态增量（Delta）
            emit("node.completed", nodeId, spanId, delta, durationMs);
            return delta;
        } catch (Exception e) {
            long durationMs = (System.nanoTime() - startNs) / 1_000_000;
            // 4. 捕获并记录失败事件，绝不吞掉异常
            emit("node.failed", nodeId, spanId, sanitizeError(e), durationMs);
            throw e;
        }
    };
}
```

这里有一个至关重要的设计：**`node.completed` 记录的仅仅是节点返回的增量（Delta），而不是整个 State 的全量快照**。如果把增量误当成全量状态，前端展示时就会误以为其他字段丢失了。全量状态是由 Graph 底层的状态机负责合并的。

### 循环场景下的最大陷阱：只用 nodeId 必死无疑

在简单的线性流里，用 `nodeId`（比如 `tool_execute`）来标识一步操作似乎没什么问题。但一旦引入了**循环（Loop）**和**多专家子图**，`nodeId` 就会彻底失效：

在退款流程中，`tool_execute` 在第一轮查订单时执行了一次，在第二轮算金额时又执行了一次；甚至在订单专家子图内部，也会使用这个名字。如果前端只根据 `nodeId` 去把“开始事件”和“完成事件”配对，迟早会把第一轮的输入误配给第二轮的输出！

因此，我们在事件模型中划分了严密的定位坐标系：

| 字段名称 | 作用与含义 |
|---|---|
| **traceId** | 整场业务运行的唯一 ID，在本项目中与该次 Run ID 保持一致 |
| **nodeId** | 业务节点名称，代表逻辑定义（如 `tool_execute`） |
| **spanId** | **每一次具体执行的唯一实例标识**。即便同一节点循环执行 5 次，也会产生 5 个完全不同的 spanId |
| **parentSpanId** | 调用链层级标识。用于将模型调用或专家子图关联到外层调度的节点上 |
| **path** | 图执行路径。主图为 `root`，专家子图为 `root/toolAgent[3]`，彻底杜绝父子图重名混淆 |
| **seq** | 单次 Run 内严格单调递增的序号，专用于前端断线重连补发与去重 |

在前端处理数据时，所有的输入与输出必须严格依据 **`spanId + path`** 进行配对，这样无论工具循环多少轮、专家嵌套有多深，链路数据永远清清楚楚。

## 实时推送与 SSE 竞态避坑

后端在内存的 `RunStore` 中按序维护事件列表，并通过 Server-Sent Events（SSE）将事件流推送给前端。座舱后端基于 Spring WebFlux 响应式栈，对外暴露 `Flux<ServerSentEvent<TraceEvent>>`。

在实现这套机制时，我们踩过两个非常隐蔽的工程坑：

### 1. 订阅时的微秒级竞态丢失
当用户打开页面订阅一个正在运行的任务时，常规逻辑是：先去历史列表里把游标之前的事件发给客户端，然后把客户端的连接注册到实时监听队列里。

但如果你这样写：
```java
// 错误示范：存在微秒级竞态！
List<TraceEvent> history = run.getHistoryAfter(lastSeq);
sendHistory(history);
// <-- 如果刚好在这微秒之内，有新节点执行完成并发射了事件...
run.subscribe(clientListener); // 这个新事件既不在 history 里，也没被 listener 捕获！
```
这个微小的间隙会导致关键的 `node.completed` 事件凭空蒸发！前端的节点就会永远卡在“执行中”的呼吸灯状态。

**解决方案**：在 `Run` 对象的并发锁内原子化完成“补发历史”与“登记监听者”，确保事件序列毫无断层。

### 2. Nginx 代理缓存导致“假实时”
联调上线后，我们曾发现一个诡异现象：本地运行很流畅，但一走线上 Nginx 代理，页面在运行过程中毫无动静，等后端全部执行完毕后，页面突然“瞬间亮起整条链路”。

原因在于 Nginx 默认开启了反向代理缓冲，它把 SSE 的数据块攒在缓冲区里，直到连接关闭才一次性冲刷。必须显式返回响应头：
```http
X-Accel-Buffering: no
Cache-Control: no-cache
```
让 Nginx 明白这是一个不能缓冲的实时流。

## 前端回放：用数组前缀优雅搞定时间线

相比后端的严谨控制，前端的时间线回放机制在架构上实现得极其优雅：

前端收到 SSE 数据后，只管把事件原汁原味地追加进一个全局响应式数组 `events` 中。界面的所有渲染状态，完全由一个计算属性（`computed`）驱动：

```typescript
// 实时模式取全量，回放模式只截取游标之前的数据
const visibleEvents = computed(() =>
  trackLive.value ? events.value : events.value.slice(0, cursor.value)
)
```

图上每个节点的当前状态（未执行 / 运行中 / 已完成 / 失败）、执行次数、经过的边高亮、当前轮次的工具卡片，全部从 `visibleEvents` 中纯函数式计算派生出来。

这意味着：**我们根本不需要为每个节点分别去写倒带动画或维护复杂的计时器状态**。拖动游标，实际上就是改变切片长度，整张图瞬间自动同步回到那个历史瞬间！

![智能座舱停在订单专家的一次工具结果：事件游标、输入输出与调用路径](/images/cockpit-agent-replay.png)

这里也有两个需要留意的细节：
1. **游标是指针索引，不是 seq**：因为单个节点执行会产生 `edge.traversed`、`node.started`、`node.completed` 等多条事件，所以单步前进不能简单把 `seq + 1`，而是要在数组中跳跃查找下一个 `node.completed` 所在的位置；
2. **工具失败与节点完成的区别**：当外部 HTTP 工具超时被业务代码捕获并妥善包装时，返回的是 `toolOutcome.ok = false`。在 Graph 看来，节点自身已经成功完成了“产出一条失败事实”的使命，因此节点事件是 `node.completed`，但工具卡片会渲染醒目的红色失败标签。**单纯看节点绿没绿，不足以判断业务动作是否成功**。

### 一次真实的线程池排障实录

在上线前的全量在线回归测试中，我们曾遇到一次极为诡异的偶发失败：
工作流已经顺利完成了第一轮超时自愈、订单查询与退款试算，眼看着答案都要生成了，却突然在最后的 `review` 评审节点意外暴毙。

如果按照过去的黑盒调试方式，大家第一反应肯定又是：“是不是模型又抽风了？或者是退款接口连不上了？”

但打开这份节点监控记录一查，报错信息一目了然：
`java.lang.OutOfMemoryError: unable to create new native thread`。

原来根本不是业务逻辑或大模型的问题！智能座舱里跑着 WebFlux 反应式线程、SSE 长连接分发、HTTP 客户端以及独立子进程 MCP Server，高频并发下的线程开销触碰到了生产容器默认的 90 线程额度上限。我们把额度上调到 128，问题立刻烟消云散。

**这就是结构化执行记录的最大意义：它把原本玄学、不可控的 AI 执行黑盒，重新拉回到了现代软件工程透明、可度量、可排查的阳光之下。**

## 状态持久化与工程沉淀

为了让这套系统在生产环境真正好用，我们做了轻量而可靠的落盘设计：
- 每当主图根节点执行完毕、任务异常中断或转入人工等待时，系统会将当前快照写入 `shared/workflow/runs` 目录下的 JSON 文件；
- 写入时采用“先写临时文件，再原子替换（Atomic Rename）”策略，避免进程崩溃导致文件损坏；
- 磁盘存储不随前端打包或后端 JAR 发布而清理，重启或发布后，历史演示与回放记录依旧完整可用。

目前默认保留最近 100 条运行记录，并在页面历史抽屉中展示最近 40 条。所有公开字段均做了脱敏处理，去除了敏感凭据与原始图片二进制流。
