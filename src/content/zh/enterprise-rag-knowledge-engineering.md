---

企业知识库最容易制造一种错觉：只要文档已经向量化、聊天框能够返回一段流畅文字，RAG 就算完成了。实际使用一段时间后，我越来越确定，模型只是整条链路的最后一棒。答案不可靠时，问题经常发生在它看到上下文之前：标题丢了、表格被打平、合同号没有被召回、旧制度压过新制度，或者一句“刚才那个规则呢”被当成了没有主语的新问题。

我最近对[企业智能座舱](/smartCockpit/)做了一次知识工程升级。目标不是换一个更大的模型，而是让“为什么召回这些证据”变得可解释、可测试、可持续改进。下面记录这次改造后的方法和取舍。

## 先把 RAG 拆成两条生产线

RAG 不是一次向量查询，而是索引链与查询链的组合：

```text
索引链：文件 -> 解析/结构恢复 -> 分块 -> provenance -> embedding -> 索引
查询链：问题 -> 查询理解 -> 权限/时效过滤 -> dense + keyword -> 融合重排 -> 上下文 -> 回答与引用
```

这两个方向都可能丢失信息。索引链丢掉标题层级后，后面的 embedding 再准确，也只会看见失去业务语境的句子；查询链忽略版本和有效期后，召回越准，越可能坚定地引用一份已经作废的制度。因此调优不能只盯模型提示词，而要从“原始事实怎样进入系统”一直追到“哪些证据进入上下文”。

这也改变了排障顺序。遇到错误回答，我现在先检查：

1. 原文是否被正确解析，标题、段落和关键编号是否还在；
2. 正确片段是否进入候选集；
3. 候选是否被过滤、融合或去重误伤；
4. 最终上下文是否包含冲突版本；
5. 最后才检查模型是否正确使用了证据。

这个顺序能把“模型不聪明”拆成几个可以复现的工程问题。

## 分块不是切字符串，而是保存最小业务语境

旧实现按固定字符窗口切分。它稳定、简单，但会把标题和正文分开，也可能在句子中间落刀。新实现先识别 Markdown 标题、中文章节标题、编号标题、空行段落和句末边界；只有结构单元仍然过大时，才退回字符窗口。每个子块会携带所属章节，例如：

```text
章节：退款审批规则
退款申请应在签收后七天内提交，并附订单号和付款凭证。
```

这样即使某个 chunk 独立进入 top-k，它仍然知道自己属于什么规则。相邻块保留有限重叠，入库前对完全重复块做指纹去重；查询后若同一文档的相邻块都得分较高，再按原顺序合并并消除重叠文本。这个组合同时处理了两个常见问题：切得过碎导致语义断裂，以及重叠 chunk 重复占满上下文。

解析也需要留下可追溯信息。当前导入会保存 `source`、`sourceType`、`parser`、`ingestedAt`、`contentHash` 和 `chunkStrategy`。它们不直接让答案变聪明，却能回答几个很关键的问题：这段知识从哪里来、用什么解析器处理、何时进入系统、内容有没有变化、历史数据采用哪一版分块策略。没有这些 provenance，重建索引后出现质量波动时往往只剩猜测。

## Dense 与关键词不是二选一

语义向量擅长找到“意思相近但表述不同”的内容；关键词检索擅长合同号、SKU、错误码、版本号和专有名词。企业问题通常同时包含两类信号。只用向量，`CN-2026-0818` 这样的精确编号可能被语义更相近的通用合同规则压过；只用关键词，“离职后还能报销吗”又可能错过标题为“劳动关系终止后的费用结算”的章节。

当前座舱同时取两路候选：

```text
dense_candidates   = pgvector.cosine(query, candidate_k)
keyword_candidates = mysql.lexical(query, identifiers, candidate_k)
fused              = RRF(dense_candidates, keyword_candidates)
ranked              = boost_exact_identifier_phrase_version_freshness(fused)
context             = merge_adjacent(dedupe(ranked), top_k)
```

融合采用 Reciprocal Rank Fusion。它使用名次而不是强行比较两套不可直接对齐的分数，因此实现简单、参数稳定。之后再给完整短语、业务编号、标题命中、新版本和较新的导入时间施加有限加分。重排的原则是“小幅纠偏”，不让某一个手工规则完全接管相关性。

更重要的是，两路候选也是降级设计。向量连接临时异常时，关键词链仍可给出证据；关键词数据库出问题时，dense 候选仍能工作。混合检索提升的不只是平均质量，也提升了链路韧性。

## “最新知识”必须是数据模型的一部分

文档库里最危险的不是没有答案，而是同时存在三份看似权威、实际互相冲突的答案。仅按相似度排序不会理解“草稿”“已废止”或“下月生效”。

这次改造把知识状态显式放入 metadata：

| 字段 | 作用 |
| --- | --- |
| `status` | 默认只检索 active、published、current 等有效状态 |
| `effectiveFrom` | 尚未生效的制度不进入普通查询 |
| `effectiveTo` | 已过有效期的知识默认排除 |
| `supersededBy` | 被新文档替代的版本默认排除 |
| `version` | 多份候选相关度接近时轻量偏向新版本 |

管理员仍可在诊断场景显式包含失效知识，但普通问答不应该让用户承担版本判断。再向前一步，还应把“发布新版本时自动标记旧版本”“定期扫描孤儿向量和过期文档”做成维护任务。知识库的更新机制和搜索算法同样重要。

## 多轮对话需要先补全检索问题

对话模型能看懂“刚才那个”，向量检索却只拿到当前字符串。若上一轮问“退款期限是什么”，下一轮问“该规则适用于谁”，直接 embedding 第二句很容易召回一堆泛化内容。

当前实现对明显包含指代词的追问，拼接最近一条用户问题形成检索查询：

```text
退款期限是什么？
后续问题：刚才的规则适用于谁？
```

原问题仍然用于生成回答，补全后的文本只服务检索。这个保守规则没有让模型随意改写所有查询，避免引入新的不可控变化；后续积累真实问答集后，再考虑用小模型做结构化 query rewrite，并比较改写前后的 recall@k。

## MCP Tool 与知识库要各司其职

知识库适合相对稳定、可引用的事实；MCP 工具适合实时天气、地图、计算器、业务查询等需要执行或读取即时状态的能力。两者不应该互相伪装：过期天气不该作为知识文档回答，制度条款也不需要每次通过工具调用重新读取。

工具侧还有一个容易被忽略的边界：模型只能规划界面明确暴露并由用户选择的工具。以前“开启工具但未选择”会隐式赋予一个默认天气工具；现在空选择就是空权限。宿主根据 MCP schema 校验参数、限制步骤、执行调用并记录轨迹，模型负责在已授权目录里规划，而不是自行发明能力。

这使 MCP 从“让模型随便调用函数”变成一条可审计链：

```text
用户选择 -> 工具目录/schema -> 模型计划 -> 宿主校验与有限执行 -> observation -> 最终回答
```

## 没有检索实验台，就很难形成调优闭环

过去检索结果藏在聊天回答后面。答案不好时，要靠日志猜测是召回错了还是模型用错了。现在知识库页面增加了 Retrieval Lab：选择知识库，直接输入问题，界面显示 Hybrid + RRF 的命中顺序、得分、摘要和完整证据。后端对应的受保护接口复用真实检索链，不另造一套“测试算法”。

可见性只是第一步。接下来应维护一组小而真实的黄金问题集，每条包含：允许的知识库、期望文档或片段、关键事实、是否应该调用工具。每次调整 chunk、embedding、融合权重或 metadata 规则后，至少比较：

- `Recall@k`：正确证据是否进入候选；
- `MRR`：第一个正确证据排得是否足够靠前；
- 引用正确率：回答中的断言能否被引用片段直接支持；
- 冲突/过期命中率：失效知识是否混入上下文；
- p50/p95 延迟和候选规模：质量提升是否以不可接受的响应时间换来。

还要记录“无答案”。系统知道自己没有证据，比从无关 chunk 拼出一个流畅答案更有价值。Retrieval Lab 的空结果提示会引导检查文档状态、有效期、metadata 和分块内容，而不是立刻把 top-k 调大。

## 这次升级带来的结论

这次实践让我形成了一个更朴素的判断：企业 RAG 的核心资产不是向量库，而是可维护的知识生产与检索反馈系统。模型升级可以提升表达和推理，但它不会自动修复错误解析、缺失权限、过期制度和糟糕的候选集。

如果要给实施顺序排优先级，我会选择：

1. 先保证文档结构、来源和生命周期可追溯；
2. 再让语义与关键词检索互补，并把候选过程暴露出来；
3. 用真实问题集建立指标和回归测试；
4. 最后再比较 embedding、reranker 和生成模型。

这样做的好处是，每一次优化都能回答“改善发生在哪一层”，每一次退化也能快速定位。一个可调优的知识系统，应该允许团队修正数据、规则和评价集，而不是只能继续修改提示词。

当前版本可以在[企业智能座舱](/smartCockpit/)体验，知识库页面已经包含检索质量测试入口。
