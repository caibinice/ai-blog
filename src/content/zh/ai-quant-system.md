刚开始接触 AI 量化时，我最容易被吸引的是结果：一条上扬的净值曲线、一组看起来很漂亮的收益指标，或者一句“模型发现了市场规律”。真正动手以后，我才意识到，量化项目最难的部分并不是把某个公式写出来，而是回答一连串更朴素的问题：数据是什么时候得到的？任务失败后能不能重跑？模型的判断能不能追溯？回测有没有偷看未来？

这些问题都不性感，却决定了一个系统到底能不能被信任。于是，我没有把这个项目做成一个孤立的选股页面，而是把它当作一套研究系统来构建——它要能被复查、能被重复、也能在我发现问题时把证据交出来。

## 一条完整的研究闭环

前端使用 React 和 Vite，负责呈现行情、股票池、因子排行、舆情、回测、Walk-forward、任务状态与学习课程。FastAPI 后端只承担清晰的接口职责；真正耗时的数据同步、模型分析和回测由独立 Worker 执行。MySQL 不只是结果仓库，也保存任务状态、数据版本和学习进度。

一次研究任务的生命周期是：

1. 页面提交研究参数，API 把任务写成 `queued`；
2. Worker 认领任务，将状态更新为 `running`；
3. 数据采集、情绪分析或回测逐步写回进度；
4. 成功后保存结构化结果，失败则记录可读错误并允许重试；
5. 页面刷新或服务重启后，任务状态仍然存在。

![研究任务的数据流与生命周期：前端 → FastAPI → 单 Worker → MySQL，任务状态可持久、失败可重试](/images/ai-quant-system-flow.svg)

这个设计并不追求夸张的吞吐量。服务器只有 2 核 2GB，单 Worker 串行执行反而更可控：不会让行情采集、大模型请求和 pandas 回测同时制造内存峰值，也更容易定位失败发生在哪一层。

## 状态机才是这套系统的地基

把“任务”当成一个有状态的对象，而不是一次性的函数调用，是整套设计里最关键的一步。每个状态都对应一次明确的写库动作：提交时写 `queued`，认领时写 `running`，结束时写 `success` 或 `failed`。状态不是留在某个进程的内存里，而是落在数据库的一行记录上。

这带来一个容易被忽略的好处：进程随时可以死。Worker 崩溃、机器重启、我手滑 kill 掉服务，任务的状态都不会跟着消失。重启后，`running` 却没有对应活着进程的任务会被视为中断，可以重新排队；`success` 与 `failed` 则原样保留。换句话说，“状态在重启后仍然存在”不是一句宣传语，而是把状态放进数据库这个决定的自然结果。

![研究任务的状态机：queued → running →（success 或 failed），失败可重试回到 queued，成功落库持久化](/images/ai-quant-system-state.svg)

失败这一步我特意做得啰嗦一点。任务失败时，我不只把状态改成 `failed`，还会把一段人能读懂的错误信息写进同一行——是数据源超时，还是某只票停牌导致缺数据，还是回测区间里出现了异常值。等我第二天回来看，读的是“为什么失败”，而不是一个空的红点。

重试则要求幂等。重跑一个任务，不应该在库里留下两份半成品结果。我的做法是让每次执行先清理这次任务此前写入的派生数据，再重新计算；原始数据只补齐、不覆盖。用一段示意伪代码表达这个转移逻辑（仅为示例）：

```python
# 示例：任务状态转移，非真实项目代码
def run_task(task):
    task.mark("running")            # 认领，写库
    try:
        clean_previous_outputs(task)  # 保证重试幂等
        result = execute(task)        # 采集 / 情绪 / 回测
        task.save(result)
        task.mark("success")          # 结构化结果落库
    except Exception as e:
        task.mark("failed", error=readable(e))  # 可读错误
        # 不在这里静默吞掉，留给人或重试策略决定
```

## 数据也要有版本

如果只存“最新数据”，那么昨天那次回测就永远无法被诚实地复现——因为脚下的数据已经变了。所以我给数据也记上获得时间与版本：一次采集是一个可标识的批次，回测引用的是某个版本，而不是“当时恰好是什么”。

这件事的价值在换数据时才会显现。当我说“换一批数据仍能复现实验”，前提就是旧的那批还在、还能被指名引用。数据版本化不追求多花哨，它只是让“可复现”从一句愿望变成一个可以检查的属性。

## 让 AI 负责“可审计的判断”

我把大模型主要放在新闻和公告的结构化抽取层：它输出利好、中性或利空标签，同时给出分数、置信度、摘要和理由。模型结果会带着模型名与分析时间保存，原文仍然保留。

字段是刻意设计的。除了标签，我还留下分数、置信度、摘要、理由、模型名和分析时间。这样每一条判断都自带上下文：它是谁在什么时候、以多大把握、基于哪句话得出的。一条示意性的抽取结果大致长这样（字段为示例）：

```json
{
  "label": "bullish",
  "score": 0.62,
  "confidence": 0.71,
  "summary": "季度营收指引上调",
  "reason": "公告提到下季度出货预期高于市场共识",
  "model": "llm-extractor",
  "analyzed_at": "2026-05-11T09:20:00Z"
}
```

这里有一条我一直守着的原则：原文不可变，派生可重算。原始文本是事实，存进去就不再改动；标签、分数这些都是从原文推导出来的，模型换了、prompt 改了，我可以对同一批原文重新跑一遍，得到一份新的派生结果，而不必担心污染了源头。

这意味着我可以分别检查两件事：

- 模型究竟从文本中读出了什么；
- 策略怎样使用这条结构化信息。

仓位和交易规则仍由确定性的因子组合与回测代码负责。这条职责边界是我故意划下的：AI 擅长从非结构化文本里读出倾向，但它的输出带着不确定性；而因子计算和回测必须是确定的——同样的输入永远得到同样的输出，否则回测就失去了意义。让 AI 去抽取、让确定性代码去决策，两边的错误就不会互相掩盖。这样做也许不够“全自动”，却让我能在结果异常时找到证据，而不是面对一个只会给结论的黑盒。

## 研究系统也应该是一套学习系统

项目里还放入了十一章零基础课程和可运行实验。它们从 K 线、Python 与 pandas 开始，一直走到可信回测、舆情因子、Walk-forward 和研究工程化。学习进度先保存在浏览器，API 可用时再同步到 MySQL。

这套课程其实是一条能力阶梯：先能看懂 K 线、会用 pandas 处理时间序列，再理解一次回测怎样才算“可信”（不偷看未来、不幸存者偏差），然后才谈得上把舆情做成因子，用 Walk-forward 检验它是否只是过拟合，最后回到研究工程化——也就是本文一直在讲的任务、状态、版本这些看似不起眼的底座。顺序不能颠倒：跳过可信回测直接追因子，追出来的多半是自欺。

我越来越认同一个看法：真正的成果不是某次回测跑出了高收益，而是明天换一批数据、换一个时间窗口、甚至换一台机器后，我仍能解释实验、重复实验并承认它的限制。

## 当前边界

这个系统只做研究和教学，不连接券商，也不会执行真实交易。这不是偷懒，而是因为真实下单要面对的问题，教学系统根本没有认真处理：停牌时挂单会怎样、触及涨跌停能不能成交、大单的冲击成本有多少、策略容量到哪里就失效、数据授权是否覆盖实盘用途、行情断线时如何安全恢复。这些每一条都可能让一个纸面上漂亮的策略在真实市场里赔钱。

在没有完成这些工作之前，“自动下单”不是进度，而是在越过证据。我宁可让这套系统停在“能解释、能复现、能追溯”的位置上，也不急着给它接上真金白银。

可以在 [/quant/](/quant/) 打开当前运行版本。它更像一间持续装修的实验室，而不是一台承诺答案的机器。
