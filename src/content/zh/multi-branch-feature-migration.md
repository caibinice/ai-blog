title: 代码遴选(Cherry-pick)的最佳实践：多工厂部署下的分支治理
excerpt: 给多个工厂分别部署同一套系统时，跨工厂复用功能如果靠分支互相合并，迟早会失控。我的做法是让 cherry-pick 只走一条路：每个功能先在主干上收敛成一个干净提交，再遴选到需要它的工厂。
---

给多个工厂分别部署同一套系统，是我在实际项目里反复打磨的一件事。同一套 Java + Vue 代码要在不同工厂现场落地，每个工厂都有自己的部署分支，设备地址、产线配置、数据库脚本各不相同。可功能又是大量共享的——工厂 A 打磨好的一个日志平台，工厂 B、工厂 C 多半也想要。

问题就出在“想要”上。把功能从一个工厂搬到另一个，最省事的想法是把分支合并过去，而这恰恰是最容易埋雷的做法。这篇写写我最后收敛出来的一套规矩：跨工厂复用功能，只让 `cherry-pick`（代码遴选）走一条路。

## 先分清三类分支的角色

动手之前，得先承认这套仓库里的分支不是平级的，它们分三类：

- **公共主干 `prod_main`**：存放所有工厂都能复用的、干净的功能提交。它不对应任何一个现场，是共享功能的“集散地”。
- **工厂部署分支 `prod_factory_a`、`prod_factory_b`……**：每个工厂现场真正部署运行的分支，带着各自的专属配置。
- **已弃用的根分支**（早期的 `main`、`prod` 之类）：不再作为开发、遴选或发布的基线，留着只是历史。

有个坑要专门说：有些部署分支名字里带 `main`（比如某个工厂的 `factory_c/main`），它**不是**根分支，也不是公共主干，它只是那个工厂的部署分支而已。名字会骗人，角色不会。

一句话记住整套流程：**跨工厂的功能只走一条路——源工厂部署分支 →（在主干上收敛成一个提交）→ 目标工厂部署分支。**

## 一条铁律：部署分支之间不互相合并

最直觉、也最危险的做法，是把做好功能的那条分支直接合并到目标工厂：

```
# 反例，别这么干
git switch prod_factory_b
git merge origin/prod_factory_a
```

一旦这么做，工厂 A 的设备调用、专属配置、初始化脚本会连同你真正想要的那个功能一起涌进工厂 B。当下编译能过，问题往往几周后才在现场冒出来——某个写死的设备地址被悄悄带了过去。部署分支代表的是“这个工厂此刻真实运行的样子”，它们彼此之间就不该发生合并。

正确的路径是两段式：先把源工厂的若干提交遴选、筛选、收敛成主干上的一个干净提交，再由目标工厂从主干遴选这一个提交。

## 一个功能，在主干上只留一个提交

一个功能在源工厂往往是零散长出来的：先建模块，再补 Service 和 Mapper，调 Controller，顺手改了配置，还可能混进这个工厂专属的调用。照搬这段提交历史没有意义，也没法复用。

所以进主干时，我不搬历史，只搬结果：

```
git switch prod_main
git cherry-pick -n <源提交1> <源提交2> <源提交3>
```

`-n` 是 `--no-commit`：它把这几笔改动一起铺到工作区，却**不**急着生成提交，把“到底哪些该留”的决定权交回给我。接下来才是真正花时间的一步——逐个文件看 diff，回滚掉工厂专属的东西，删掉不需要的目录，依赖清单只保留最小接线。筛完、编译测试都通过，才合成一个提交：

```
git commit -m "feat(common): add log platform"
```

到这里，这个功能在主干上就有了唯一一个干净的提交号。这样做的好处很实在：分支数量不再膨胀；哪个工厂用了这个功能、什么时候用的，翻一遍主干提交历史就知道；要回滚，也只是回滚那一个提交而已。

## 第一段：从工厂 A 整理到主干

动手前我有个 30 秒习惯：`git status` 确认工作区干净、`git fetch origin --prune` 更新远程、确认自己站在 `prod_main` 而不是某个根分支，最后**记下当前 `prod_main` 的 SHA**当回滚点。

然后切到并更新主干：

```
git fetch origin --prune
git switch prod_main
git pull --ff-only origin prod_main
```

在源工厂分支上查清楚要搬哪几笔，别只看提交标题，要看文件清单和 diff：

```
git log origin/prod_factory_a --oneline --decorate
git show --stat <源提交>
```

重点确认三件事：这几笔改了哪些文件、有没有夹带工厂专属的设备地址或接口、几笔之间有没有前后依赖。看清楚了，再按顺序 `cherry-pick -n` 全部铺到工作区，然后进入筛选——这一步用 IDE 的图形化 diff 最顺手：保留可复用的内容，对工厂专属文件选择回滚，对不该进来的新目录直接删，POM 只留必要的模块声明和依赖。筛完过一遍编译和测试，确认工作区只剩本功能该有的文件，再合成那**一个**提交并推送。

## 第二段：工厂 B 从主干遴选

第二段轻得多，因为主干上已经是一个筛过、测过的干净提交了：

```
git switch prod_factory_b
git pull --ff-only origin prod_factory_b
git cherry-pick -x <主干功能提交SHA>
```

`-x` 会把来源提交号写进新提交的说明里，日后一眼能追溯这个功能从哪来。如果工厂 B 需要额外适配，**单独再提交一笔**，绝不把适配混回主干那个公共提交。最后编译测试通过再 push。

## 一个完整案例：把日志平台搬到工厂 B

抽象讲总有点空，上一个真实做过的例子（信息已脱敏）。

工厂 A 现场做了一个日志平台，现在工厂 B 也要。相关的改动散在源分支的三笔提交里：

| 源提交（示例） | 内容 | 为什么不能逐笔照搬 |
|---|---|---|
| `a1c9f0e` | 把日志管理整合成独立模块 | 同时移动了多个旧模块文件、改了多个 POM |
| `b2d47a1` | 建日志模块的核心内容 | 混进了未完善的 starter 和工厂 A 专属调用 |
| `c3e8b90` | 把 Service、Mapper、实体迁入日志模块 | 同时动了线程池、现场服务和旧模块文件 |

所以要先 `-n` 汇总，再筛选。哪些进主干、哪些坚决排除，我提前列成白名单：

![案例筛选去向：进入 prod_main 的是日志模块与最小 POM 接线，排除的是独立 starter、工厂专属调用、外围改动与前端脚本](/images/cherry-pick-selection.svg)

**允许进入 `prod_main`**：日志模块目录 `log-platform/**`、两个后台 Controller、模块内的配置类，以及三个 POM 里最小的模块声明与依赖接线。

**明确排除**：独立的 `log-platform-starter` 模块（连同根 POM 里对它的 `<module>` 声明）、工厂 A 的工单与设备调用、没被明确批准的线程池等外围改动、以及前端页面和数据库初始化脚本。

第一段，把三笔汇总到主干后筛选、编译、合成一个提交：

```
git switch prod_main
git pull --ff-only origin prod_main
git cherry-pick -n a1c9f0e b2d47a1 c3e8b90
git restore --staged .
# 在 IDE 里回滚白名单外的文件，删掉多余目录，POM 只留最小接线
git status --short          # 确认只剩白名单内容
mvn -pl log-platform -am clean test
git add log-platform
git add -p pom.xml          # POM 只挑需要的片段
git commit -m "feat(common): add log platform"
git push origin prod_main
```

记下这一步生成的 SHA，它就是日志平台在主干上唯一的公共功能提交号。

第二段，工厂 B 遴选这一个提交，跑通测试再推：

```
git switch prod_factory_b
git pull --ff-only origin prod_factory_b
git cherry-pick -x <上一步的主干SHA>
mvn -pl log-platform -am clean test
git push origin prod_factory_b
```

最终三条分支各就各位：工厂 A 分支保留它原来那几笔提交和适配；主干上多了一个干净的日志平台提交；工厂 B 分支遴选了主干这一个提交，需要的话另加自己的适配提交。以后工厂 C 要用，也只是从主干再遴选这同一个提交而已。

## 遴选冲突与回滚

`cherry-pick` 撞上冲突是常事。解决冲突、`git add` 之后 `git cherry-pick --continue` 继续；想整个放弃这次遴选，`git cherry-pick --abort` 回到干净状态。

操作错了要回退，分两种情况。**还没 push**：`git reset --hard <操作前记下的SHA>`，再用 `git clean -nd` 预览、确认无误后 `git clean -fd` 清掉多余文件——这就是为什么我总在动手前先存一份 SHA。**已经 push 到主干**：别强推、别改写公共历史，老老实实 `git revert <错误提交>` 造一个反向提交；如果别的工厂已经遴选过那个错误提交，它们也各自 `revert` 一次。

## 提交信息也要能追溯

提交说明我按用途分类，好让主干历史自解释：公共功能用 `feat(common): ...`，某工厂的适配用 `feat(factory-b): ...`，公共修复用 `fix(common): ...`。别再出现“修改代码”“功能调整”这种一个月后谁都看不懂的提交。

## 写在最后

跨工厂协作里最贵的从来不是写功能，而是事后搞不清某段代码为什么会出现在这个工厂。`cherry-pick` 用好了，本质上是一种纪律：让每个共享功能在主干上只留一个干净、可追溯、能一键回滚的提交，其实是在给未来的自己省下解释成本。
