---
title: 一个功能只留一个提交：多工厂部署下的分支治理
excerpt: 给多个工厂分别上线同一套系统时，我不再让部署分支互相合并，而是让每个可复用的功能先在主干上收敛成一个干净提交，再遴选到需要它的工厂。
---

给多个工厂分别上线同一套系统，是我在项目里踩过的一类坑。每个工厂现场都有自己的部署分支，设备地址、产线配置、数据库脚本各不相同；但很多功能是通用的——一个工厂打磨好的日志平台，别的工厂多半也想要。麻烦就藏在“想要”这两个字里。

## 部署分支之间不该有合并关系

最直觉的做法，是把做好功能的那条分支直接合并到目标工厂：

```
git switch prod_factory_b
git merge origin/prod_factory_a
```

一旦这么做，工厂 A 的设备调用、专属配置、初始化脚本会连同你真正想要的那个功能一起涌进工厂 B。当下编译能过，问题往往几周后才在现场冒出来——某个写死的地址被悄悄带了过去。部署分支代表的是“这个工厂此刻真实运行的样子”，它们彼此之间不应该发生合并。

我后来给自己立的规矩只有一条：跨工厂的功能只走一条路——源工厂分支 → 主干上的一个提交 → 目标工厂分支。中间不再开临时分支，主干（我把它叫作 `prod_main`）上那个干净提交，就是唯一的中转单位。

## 让功能在主干上收敛成一个提交

一个功能在源工厂往往是零散长出来的：先建模块，再补 Service，调 Controller，顺手改了配置，还可能混进这个工厂专属的调用。照搬这段历史没有意义。我的做法是先把需要的几笔提交摘到工作区，但先不生成提交：

```
git switch prod_main
git cherry-pick -n <提交1> <提交2> <提交3>
```

`-n` 是 `--no-commit`，它把改动铺到工作区，却把“到底要不要”的决定权交回给我。接下来才是真正花时间的一步：逐个文件看 diff，回滚掉工厂专属的东西，删掉不需要的目录，依赖清单只留最小接线。筛完、编译测试都跑通，再合成一个提交：

```
git commit -m "feat(common): add log platform"
```

到这里，这个功能在主干上就有了唯一一个干净的提交号。

## 其他工厂只需遴选这一个提交

哪个工厂要用，就从主干把这一个提交摘过去：

```
git switch prod_factory_b
git cherry-pick -x <主干提交SHA>
```

`-x` 会在新提交里记下来源提交号，方便日后追溯。如果目标工厂需要额外适配，就单独再提交一笔，绝不把适配混回主干那个公共提交。

这套流程真正让我省心的，不是它多优雅，而是它把复杂度摁住了：分支数量不再膨胀，每个通用功能都对应一个能一眼认出的提交，谁用了、什么时候用的，翻一遍提交历史就知道。要回滚，也只是回滚那一个提交而已。

## 出错了怎么办

还没 push，就 `git reset --hard` 回到操作前记下的那个 SHA——所以我总在动手前先存一份。已经 push 到主干，就别强推、别改写公共历史，老老实实用 `git revert` 造一个反向提交；如果别的工厂已经摘过这个错误提交，它们也各自 revert 一次。

跨工厂协作里最贵的从来不是写功能，而是事后搞不清某段代码为什么会出现在这个工厂。让每个功能只留一个提交，本质上是在给未来的自己省下解释成本。
