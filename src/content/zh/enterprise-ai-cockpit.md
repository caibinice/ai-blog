很多 RAG 演示都从一个聊天框开始：上传文件、输入问题、模型给出回答。这个流程适合证明概念，但当我尝试把它变成企业智能座舱时，问题很快超出了聊天本身。

知识库和文档是否持久化？删除文档时向量如何同步？回答引用了哪些分块？上游模型流式中断后怎样反馈？经营报告、数据源和对话记录怎样共享一套权限与审计边界？

这个项目就是在回答这些更接近真实落地的问题。

## 两类数据库承担不同职责

MySQL 保存知识库、文档元数据、数据源、报告模板、运行记录、对话和业务配置。PostgreSQL + pgvector 保存固定维度的向量与分块 metadata。

文档导入后，后端使用 Apache Tika 提取文本，按可控大小切分，再生成 embedding 并写入向量表。提问时优先做 pgvector cosine 检索；如果向量服务不可用，仍可回退到 MySQL 关键词和 CJK 检索。

这种分工不是为了堆叠数据库，而是让结构化业务数据和相似度检索各自使用合适的工具，同时保留降级路径。

## 流式回答必须来自真实上游

后端使用 Spring WebFlux 与 Spring AI。`ChatClient` 接收到上游 OpenAI-compatible/DeepSeek 的 SSE 后，将 token、引用、图表信息和完成状态继续以事件流发送给 Vue 前端。

这和把完整回答在本地切成若干字符串不同。真实上游流可以更早给出反馈，也必须处理连接中断、超时、错误事件与最终状态。Nginx 需要关闭 SSE buffering，否则后端虽然逐段输出，浏览器仍可能最后一次性收到。

前端把回答文本、引用文档和 ECharts 图表放在同一上下文里。用户看到的不只是“模型说了什么”，还可以继续追问“它依据了什么”。

## 企业座舱不等于万能机器人

当前系统还包含报告模板、运行记录、数据源测试、语音接口和 MCP 天气示例。这些能力的意义，是验证 AI 如何进入一个已有工作流，而不是把所有功能都塞进对话框。

我刻意保留了几个边界：

- 本地 embedding 只用于可重复的链路验证，生产质量仍需真实模型；
- 数据源抽取和报告任务仍有 MVP 成分；
- 公网演示使用 Nginx Basic Auth，应用级 RBAC、租户隔离与审计仍是后续工作；
- 模型回答必须带引用，不能把流畅表达当成事实保证。

## 小服务器上的取舍

这套系统和另外两个项目共享 2GB 内存。前端全部在本地构建成静态文件；服务器只运行一个受限 JVM 后端。数据库连接池、Quartz 线程、堆、metaspace 和 direct memory 都设置明确上限。

如果整体资源持续超过阈值，智能座舱会成为第一个被暂停的后端。这不是失败，而是容量边界的一部分：系统应当知道什么时候保持克制。
