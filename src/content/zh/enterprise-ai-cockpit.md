很多 RAG 演示都从一个聊天框开始：上传文件、输入问题、模型给出回答。这个流程适合证明概念，但当我尝试把它变成企业智能座舱时，问题很快超出了聊天本身。

知识库和文档是否持久化？删除文档时向量如何同步？回答引用了哪些分块？上游模型流式中断后怎样反馈？经营报告、数据源和对话记录怎样共享一套权限与审计边界？

这些问题的共同点是：它们都发生在“对话之外”。聊天框只是入口，真正决定能不能上线的，是入口背后的存储、检索、事件流和降级路径。这个项目就是在回答这些更接近真实落地的问题。它不追求把功能做全，而是把从上传到回答这一整条链路上每一个会“悄悄失败”的环节都显式化出来。

## 两类数据库承担不同职责

MySQL 保存知识库、文档元数据、数据源、报告模板、运行记录、对话和业务配置。PostgreSQL + pgvector 保存固定维度的向量与分块 metadata。

为什么不把这些都塞进一个库？因为两类数据的访问模式完全不同。业务数据需要事务、外键、条件过滤和分页，这是关系型数据库的主场；向量检索需要的是“给定一个查询向量，找出最相似的 top-k”，本质是近似最近邻搜索。把高维向量塞进普通表再逐行算距离，既慢又难维护。让每类数据各自使用合适的引擎，接口反而更干净。反过来，如果强行合并，最后总有一类操作要迁就另一类的存储结构，读写路径都会被拖累。

文档导入是一条可以拆解的链路：

- Apache Tika 从 PDF、Word、纯文本等格式里提取纯文本，屏蔽格式差异；
- 按可控大小切分成 chunk，比如每块 500 字符、重叠 50 字符（此处数字仅为示意，实际按语料和 embedding 模型调整）；重叠是为了避免把一句话从中间切断后丢失上下文；
- 对每个 chunk 生成 embedding；
- 把向量连同 chunk metadata（属于哪个文档、第几块、原文位置）写入向量表。

把这条链路写成伪代码，边界会更清楚：

```text
# 导入（index path）
text   = tika.extract(file)                   # 屏蔽 PDF/Word/纯文本差异
chunks = split(text, size=500, overlap=50)    # 数字为示意，需按语料调整
for c in chunks:
    v = embed(c.text)                         # 生成固定维度向量
    pgvector.insert(v, meta={doc_id, idx, span})
mysql.save(doc_meta)                          # 业务侧登记文档
```

metadata 之所以重要，是因为检索命中的是向量，但用户要看的是“这句话出自哪份文档的哪一段”。没有 metadata，就没法把相似度结果还原成可核对的引用。向量本身只是一串浮点数，它能告诉你“像”，却不能告诉你“出处”，而企业场景恰恰更在意出处。

chunk 的大小是个需要权衡的旋钮，不是越小越好也不是越大越好。切得太碎，单个分块承载的语义不完整，检索时容易命中半句话；切得太大，一个分块里混进多个主题，相似度会被稀释，引用也不够精确。重叠是对切割处的一种补偿：让相邻分块共享一小段边界文本，避免恰好被切断的关键句两边都丢。这几个数字最终都要落到具体语料上去试，没有一劳永逸的默认值。

提问时优先做 pgvector cosine 检索，取 top-k 最相似的分块作为上下文：

```text
# 查询（query path）
q    = embed(question)
hits = pgvector.search(q, top_k=5)            # 首选：cosine top-k（top_k 数值为示意）
if vector_unavailable or not hits:
    hits = mysql.keyword_cjk_search(question) # 回退：关键词 / CJK
context = [h.chunk for h in hits]             # 拼进上下文，附带引用
```

这里有一条我没有省略的降级路径：如果向量服务不可用——连接失败、超时或维度不匹配——检索会回退到 MySQL 的关键词与 CJK 检索。中文分词和英文不同，直接按空格切会把整句话当成一个词，所以回退检索要专门处理 CJK 才有意义。回退的结果质量通常不如向量检索，但它保证了“向量库挂了整个问答就完全不可用”不会发生。降级不是默认路径，而是明确的兜底：正常时不会走到它，一旦走到，用户至少还能拿到基于关键词的答案，而不是一个转圈的空白页。

top-k 里的 k 也要克制。取得太少，可能漏掉真正相关的分块；取得太多，无关内容会挤占上下文，反而把模型的注意力稀释掉。它和 chunk 大小是联动的：分块越小，通常需要的 k 越大才能凑齐足够的上下文。

两类存储的职责可以并列看得更清楚：

| 维度 | MySQL | PostgreSQL + pgvector |
| --- | --- | --- |
| 存什么 | 知识库、文档元数据、数据源、报告模板、运行记录、对话、业务配置 | 固定维度向量、分块 metadata |
| 访问模式 | 事务、条件过滤、分页、外键关联 | top-k 近似最近邻检索 |
| 主要用途 | 承载经营工作流的状态 | 支撑语义检索 |
| 在问答里的角色 | 关键词/CJK 回退检索 | 首选 cosine 检索 |

这种分工不是为了堆叠数据库，而是让结构化业务数据和相似度检索各自使用合适的工具，同时保留降级路径。删除文档时也因此要两边一起动：删掉 MySQL 里的业务记录，同时清掉 pgvector 里对应的向量与分块，否则检索会命中一份已经不存在的文档，引用也就失去了意义。跨两个库的删除没有天然的事务保证，所以顺序和补偿要想清楚：一种稳妥的做法是先标记业务记录为已删除、再异步清理向量，即使中途失败，也能靠一个对账任务扫出“有向量却没有对应文档”的孤儿分块并回收，而不是让它们悄悄留在检索结果里。

## 流式回答必须来自真实上游

后端使用 Spring WebFlux 与 Spring AI。`ChatClient` 接收到上游 OpenAI-compatible/DeepSeek 的 SSE 后，将 token、引用、图表信息和完成状态继续以事件流发送给 Vue 前端。

这和把完整回答在本地切成若干字符串、再定时吐出去有本质区别。本地假流式只是视觉效果，首字延迟仍然等于整个回答生成完；真实上游流则能在模型刚吐出前几个 token 时就让用户看到反馈。代价是，真实的流不再是一段干净的字符串，而是一串需要处理各种状态的事件：

```text
event: open           // 连接建立
event: token   × N    // 增量文本，逐段追加
event: citation       // 命中的引用分块
event: chart          // 结构化图表数据
event: done           // 正常结束
event: error/timeout  // 异常分支，需要显式收尾
```

用 WebFlux 承接这条流，好处是它天生按 `Flux` 的方式处理背压：上游产生一段就往下游推一段，中间不必先把整段回答攒在内存里。但异步也意味着错误不再是一个简单的 try/catch 能兜住的返回值，而是流上的一个事件，必须在流的语义里被显式建模。

关键在于最后两行。连接可能在中途断开，上游可能超时，也可能返回错误事件。这些都不能被吞掉——前端必须知道流是正常结束还是异常中止，否则界面会永远停在“正在输入”。所以后端对每一路 SSE 都要保证：要么以 `done` 收尾，要么以 `error`/`timeout` 收尾，不存在第三种“悄无声息地断了”的情况。这条不变量看起来简单，却是整个流式体验能不能被信任的地基：只要允许出现一次“没有终态的流”，前端就必须在别处加各种超时猜测去兜底，复杂度会立刻反噬回来。

还有一个容易被忽略的环节：Nginx 需要关闭 SSE buffering。默认情况下反向代理会缓冲响应，攒够一批再转发。这对普通接口是优化，对 SSE 却是灾难——后端明明在逐段输出，浏览器最后却可能一次性收到全部内容，流式体验荡然无存。关掉 buffering，事件才能穿过代理即时到达。这类问题最难排查的地方在于，本地直连一切正常，一上到代理后面才复现，很容易误判成后端没在流式输出。

![SSE 事件流时序：上游经 ChatClient 到前端，含 error 与 timeout 分支](/images/enterprise-ai-cockpit-sse.svg)

前端把回答文本、引用文档和 ECharts 图表放在同一上下文里。token 事件持续追加正文，citation 事件把命中的分块渲染成可点开的来源，chart 事件携带结构化数据交给 ECharts 绘制。用户看到的不只是“模型说了什么”，还可以继续追问“它依据了什么”。

## 一次问答的完整轨迹

把前面几块拼起来，一次问答其实穿过了整条链路。用户在座舱里发问，问题先被 embedding 成查询向量，走 pgvector 的 cosine 检索取回 top-k 分块；如果向量服务这一刻不可用，就回退到关键词与 CJK 检索。命中的分块连同问题一起组装成上下文，交给 `ChatClient` 发往上游。上游开始吐 token，后端一边转发 token 事件，一边在合适的时机补上 citation 和 chart 事件，最后以 `done` 收束——中途任何一步出错，都以 `error`/`timeout` 明确收尾。

我特意让这条轨迹里的每一步都有迹可循，是因为企业场景真正棘手的往往不是“答得对不对”，而是“答错了能不能查出错在哪”。检索命中了什么、引用了哪几段、流是正常结束还是中断，这些如果都留在日志和事件里，一次不理想的回答就能被复盘，而不是变成一句无从追问的“它就是这么说的”。

## 企业座舱不等于万能机器人

当前系统还包含报告模板、运行记录、数据源测试、语音接口和 MCP 天气示例。这些能力的意义，是验证 AI 如何进入一个已有工作流，而不是把所有功能都塞进对话框。

我理解的“座舱”是：AI 是其中一块仪表，而不是取代所有仪表的黑箱。报告有模板和运行记录，数据源可以单独测试连通性，对话有历史可回溯——这些都是让 AI 的输出能被追溯、被复核的结构，而不是一句“问它就好了”。仪表盘的价值恰恰在于每块表各司其职、读数可对照；把所有东西都塞进一个聊天框，等于把一堆读数揉成一句话，好看，但没法核对。

我刻意保留了几个边界：

- 本地 embedding 只用于可重复的链路验证，生产质量仍需真实模型；
- 数据源抽取和报告任务仍有 MVP 成分；
- 公网演示开放只读页面，聊天、上传、删除和报告运行由后端短期操作令牌保护；应用级 RBAC、租户隔离与审计仍是后续工作；
- 模型回答必须带引用，不能把流畅表达当成事实保证。

把这些边界写下来，是因为我不想让演示看起来比它实际的成熟度更高。本地 embedding 能跑通链路，不代表它的召回质量能上生产；只读演示加短期令牌能挡住随手的破坏，不代表它等于一套完整的权限体系。诚实地标出“这里还是 MVP”，比事后被人发现更省事。

最后一条是我最看重的。流畅和正确是两件事。一个能引用来源的回答，哪怕措辞普通，也比一段无从核对的漂亮话更可用。要求带引用，本质上是在给模型的自信设一个可以被检验的锚点——它说得越肯定，越应该能指出这句话是从哪段原文来的。

## 小服务器上的取舍

这套系统和另外两个项目共享 2GB 内存。前端全部在本地构建成静态文件；服务器只运行一个受限 JVM 后端。数据库连接池、Quartz 线程、堆、metaspace 和 direct memory 都设置明确上限。

为什么要把每一项都钉死上限？因为在共享内存的机器上，最危险的不是某个组件用得多，而是它没有上限。一个不设边界的连接池或线程池，会在压力下悄悄吃光内存，然后拖垮同一台机器上的其它服务。给每一项设一个明确的天花板，等于提前声明“我最多用这么多”，让容量变得可预测。可预测比“跑得更快”更重要——在这台机器上，一次不受控的内存尖峰造成的连锁故障，代价远高于省下的那点延迟。

direct memory 尤其值得单独盯。WebFlux 这类基于 Netty 的框架会用到堆外内存，它不受普通堆上限约束，配置时最容易被漏掉；一旦流量上来，堆看着还很宽裕，堆外却已经在悄悄膨胀。把它也纳入明确上限，才算真正把这台机器的内存账算全。

如果整体资源持续超过阈值，智能座舱会成为第一个被暂停的后端。这是有意的优先级安排：相比另外两个项目，它更像实验场，暂停它的代价最小。这不是失败，而是容量边界的一部分：系统应当知道什么时候保持克制。把“谁先让路”提前定好，比等到内存告急时临时抉择要稳妥得多。
